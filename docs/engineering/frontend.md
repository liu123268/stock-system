## 二、前端模块到底是什么

### 1. View：用户实际看到的页面

`LoginView.vue` 负责登录页面的输入框、按钮、提示和视觉样式。View不直接操作数据库，也不应该自己拼接所有HTTP细节。

### 2. Router：前端页面导航

Vue Router决定不同URL显示哪个页面，并通过路由守卫提供用户体验层的访问控制：

- 未登录访问工作台，跳转登录页。
- 已登录访问登录页，跳转工作台。
- 浏览器刷新后，已保存 Token 第一次进入受保护页面时调用 `/api/auth/me`；成功后在本次页面运行中复用确认状态，登录成功则直接视为已确认。只有后端明确确认 401 或账号失效才清会话并返回登录页，网络中断和超时保留会话并让目标页面展示加载失败与重试。

路由守卫不是安全边界。用户可以修改浏览器代码，所以真正的权限必须由Spring Security在后端检查。

### 3. Store：多个页面共享的状态

Pinia Store保存当前用户、JWT和是否登录。登录页、导航栏、工作台都可以读取同一份状态，不需要层层传递参数。

### 4. API：后端接口的前端封装

`api/auth.ts` 描述登录请求DTO、响应VO以及请求路径。页面不需要知道Axios的全部配置，只调用清楚的 `login()` 方法。

### 5. HTTP Client：所有请求共同经过的出口

`api/http.ts` 统一设置：

- 基础路径 `/api`
- 10秒超时
- JSON内容类型
- 自动添加 `Authorization: Bearer <JWT>`

当前响应拦截器已把后端统一错误响应转换为 `ApiError`；页面或访问错误处理函数据此决定提示、清理状态或跳转。网络错误仍保留原错误，不能把所有失败都当成 401。请求追踪尚未接入，若未来需要可在该公共出口实现。

### 6. Vite Proxy：开发环境转发站

浏览器认为自己只访问8083。Vite看到 `/api` 请求后转发到8082，因此开发阶段不需要给每个请求写完整后端地址，也减少跨域配置。

### 7. 前端目录增长规则

唯一目录规范见 [项目结构](project-structure.md#4-前端目录)，本文件只解释模块数据流。

### 完整登录调用链

```text
LoginView.vue
  -> authStore.login()
  -> api/auth.ts 的 login()
  -> api/http.ts 的 Axios实例
  -> http://localhost:8083/api/auth/login
  -> Vite代理
  -> http://localhost:8082/api/auth/login
  -> Spring Boot
  -> MySQL
```

返回时：

```text
Spring Boot返回LoginResponseVO
  -> Axios收到JSON
  -> Pinia保存当前用户和JWT
  -> Router跳转工作台
  -> 后续Axios请求自动携带JWT
```

## 三、Element Plus按需导入

### 1. 什么是组件库

Element Plus提供表单、输入框、弹窗、分页等通用组件。它建立在Vue 3之上，不是Vue的新版本。

### 2. 什么是打包体积

浏览器不能直接运行整个前端开发目录。执行 `npm run build` 时，Vite会把Vue、TypeScript、组件和样式转换、压缩成浏览器下载的JS/CSS文件，这些文件的大小就是打包体积。

包越大通常意味着：

- 首次打开需要下载更多内容。
- JavaScript解析和执行时间更长。
- 低性能设备或较慢网络下等待更明显。

### 3. 全量引入

最简单的写法是：

```ts
import ElementPlus from 'element-plus'
import 'element-plus/dist/index.css'

app.use(ElementPlus)
```

它把整套组件库及完整样式作为全局能力引入。即使当前登录页只使用输入框和表单，构建仍可能带入大量当前页面不需要的代码和CSS。

本项目第一次采用这种方式构建时，主JavaScript包约为1045KB，并触发了大包警告。

### 4. 按需引入

当前登录页只引入实际使用的组件：

```ts
import {
  ElForm,
  ElFormItem,
  ElIcon,
  ElInput,
  ElMessage,
} from 'element-plus'
```

同时只引入这些组件对应的样式。优化后的主要构建结果：

```text
公共主包：约152KB
登录页面包：约92KB
```

这不是单纯删代码，而是减少浏览器第一次进入系统时必须下载和解析的无用依赖。

### 5. 为什么登录页还能单独形成一个包

路由配置使用动态导入：

```ts
component: () => import('@/views/LoginView.vue')
```

Vite会把登录页拆成独立文件。用户访问登录页时才加载登录页代码，这叫代码分割或懒加载。

### 6. 面试回答模板

完整问答和追问统一见 [FRONTEND-02](../career/interview/04-frontend-engineering.md#frontend-02element-plus按需导入做了什么优化)。以上包体积是认证阶段历史构建记录，不是当前构建结果；没有本轮复测不能当作当前性能数字。

## 五、历史视觉演进与组件职责

> 本节液态背景与轨道视觉案例是历史实现，只用于理解组件隔离。当前布局、动效和尺寸以 [视觉规范](../architecture/ui-design-system.md) 为准；公开首页的新实现见下文 UI-07。

### 1. 参考页面不能只复制颜色

这次视觉方向来自用户提供的 Optical Motion Lab 页面。真正需要提取的是一组能够重复使用的设计规律：

- 近黑、白、灰构成主要色彩；
- 超大中文标题只出现在入口和关键空状态；
- 使用留白和清晰排版组织信息，减少卡片；
- 自主缓慢变形的液态透镜建立品牌识别；
- 表单仍然使用熟悉的输入框、按钮和错误提示。

如果只把旧页面改成黑白色，后面的空间页仍然会各写各的；如果整段复制参考页面，又会把宣传页的布局错误地带进业务工作台。因此项目使用 `docs/product/product-principles.md` 和 `docs/architecture/ui-design-system.md`，分别记录“产品为何存在”和“界面怎样保持一致”。

### 2. 设计令牌是什么

`frontend/src/styles/main.css` 中的 CSS 自定义属性就是设计令牌，例如：

```css
:root {
  --color-canvas: oklch(0.992 0 0);
  --color-ink: oklch(0.24 0.006 255);
  --color-border: oklch(0.86 0.006 255);
  --radius-control: 10px;
}
```

组件使用 `var(--color-ink)`，而不是各自写一遍颜色值。以后调整主文字颜色或输入框圆角，只修改令牌就能影响所有复用它的页面。

这叫“单一事实来源”：同一项设计决定尽量只在一个地方定义，减少不同页面逐渐变得不一致的问题。

### 3. 旧版液态背景组件（已删除）

早期视觉方案曾用 `LiquidBackdrop.vue` 组合液态视频、裁剪形状、柔和色散和自主 CSS 动画。Landing、认证和工作台改用 `DesignOrbit.vue` 等当前视觉组件后，这个旧组件及 `frontend/public/media/liquid-glass.mp4` 已在 2026-09-13 删除，不再作为项目素材保留。

旧方案特别删除了 Canvas 等高线和全部鼠标监听：

```text
旧方案
  pointermove -> 记录鼠标坐标 -> 改变线条折射 -> 用户移动鼠标时背景抖动

新方案
  video循环 + CSS关键帧 -> 按固定时间轴缓慢变化 -> 与鼠标位置无关
```

自主动画的优点不是技术更复杂，而是视觉更稳定。用户移动鼠标是为了操作页面，不应该无意中改变整张背景的形状。

### 4. `prefers-reduced-motion` 为什么重要

有些用户会因为持续移动、缩放或视差产生不适，操作系统提供“减少动态效果”偏好。页面通过下面的媒体查询响应它：

```css
@media (prefers-reduced-motion: reduce) {
  .optical-passage {
    animation: none;
  }
}
```

当前 `DesignOrbit.vue` 和行情图表等仍使用同一个偏好。减少动态时关闭对应 CSS 动画或图表动画，保留静态构图和必要内容。这样不是隐藏内容，而是只移除持续运动。

### 5. 历史认证阶段：为什么视觉重构没有影响认证功能

本次保持了这些稳定边界：

- `LoginView.vue` 与 `RegisterView.vue` 的字段和校验规则不变；
- `authStore`、Axios请求与JWT存储不变；
- 路由守卫和 `/api/auth/me` 调用不变；
- 自动化测试使用的 `.auth-submit-button` 不变；
- 新增公开首页 `/`，把受保护工作台移动到 `/workspace`；
- 登录与注册通过独立路由打开，不再常驻在首页中。

视觉层与业务层分离以后，修改排版不会要求重新编写认证链路，但仍要运行类型检查、静态检查、单元测试和生产构建，防止模板重构误删事件或属性。

### 6. 为什么代码看起来已经改了，浏览器布局却可能还是错的

该历史问题的排查、旧单列修复和验证统一见 [BUG-001](bugs/BUG-001-auth-layout-style-mismatch.md)，不能把当时单列样式当作当前认证双区规范。

## 七、从认证占位页到真实空间页面

### 1. 原来代码的作用

原来的 `HomeView.vue` 只证明“用户已经通过 JWT 进入受保护页面”，并显示创建空间的占位按钮。它没有调用空间接口，也没有真正的当前空间，因此只能作为认证阶段的过渡页。

### 2. 为什么要改

用户需要尽早看见完整产品进度，而不只是数据库和接口。`CODE-003` 把后端空间能力与前端页面组成一个可见纵切：注册登录后，用户可以创建空间并进入真实概览。这个限制只说明当前阶段已经接入哪些页面；当时股票和观点未实现，不代表整个产品只需要空间功能；当前实现范围见项目状态。

### 3. 改动后的调用链

```text
登录成功
  -> Router进入 /workspaces
  -> workspace Store调用 GET /api/workspaces
  -> 0个空间时显示内联创建表单
  -> POST /api/workspaces
  -> Router进入 /workspaces/{workspaceId}/overview
  -> workspace Store调用 GET /api/workspaces/{workspaceId}
  -> 页面显示真实名称、角色、状态和成员数
```

`frontend/src/api/workspace.ts` 只描述 HTTP 契约；`frontend/src/stores/workspace.ts` 负责共享状态、防止旧请求覆盖新空间，并由 `ensureCurrent(workspaceId)` 复用同一空间已经取得的详情。当前空间 ID 仍来自 URL，不另存 localStorage；缓存只存在于本次页面运行，切换到不同 ID、退出登录、切换空间或认证失败后仍会重新读取。

工作区四个业务页现在是 `/workspaces/:workspaceId` 下的嵌套路由，共同经过 `components/workspace/WorkspaceLayout.vue`。Layout 只负责侧栏、当前导航、退出登录、返回空间选择和桌面／移动端壳层；概览、自选、成员、设置 View 继续分别负责自己的加载、错误、归档只读和业务操作。这样修改导航只需改一处，又不会把页面业务状态塞进通用布局。

### 4.1 为什么子页面不再重复读取同一空间

原来的每个子页面都先调用 `loadCurrent(workspaceId)`，再读取自己的邀请、股票或成员数据；路由守卫同时在每次切换前调用 `/api/auth/me`。因此一次“概览 → 共享自选”会依次等待当前用户、空间详情和股票列表，回到已经访问过的页面仍完整重复。

优化后，认证 Store 只复用本次运行已经由后端确认的会话，空间 Store 只复用 URL 中同一个 `workspaceId` 的详情。页面仍调用 `ensureCurrent()`，但命中时直接返回 Pinia 中的对象；换空间时 ID 不同，自动回到真实详情接口。股票、成员和邀请接口仍各自执行后端权限校验，前端缓存没有成为安全边界。

隔离浏览器复测的稳定证据是请求链数量：首次进入 OWNER 概览仍有 `/api/auth/me`、空间详情和两条邀请读取共 4 次；随后共享自选由 3 次降为 1 次、成员由 3 次降为 1 次、设置由 2 次降为 0 次，再回概览由 4 次降为两条邀请读取。开发模式毫秒耗时受 Vite 首次转换和本机调度影响较大，因此不把单轮时间写成固定性能承诺。

### 4. 0、1、多空间为什么不同

- 0 个活动空间：用户没有可进入对象，页面直接展示创建表单；
- 1 个活动空间：登录后的默认入口自动进入唯一空间；主动点击“切换空间”携带 `reason=switch`，保留加入及归档入口，不立即跳回；
- 多个活动空间：先展示列表，由用户明确选择；
- 归档空间：与活动空间分区展示，可进入概览、成员和设置页读取历史状态，但写操作受只读边界限制。

页面还实现了加载骨架、请求失败重试、窄屏布局和明确的未开放操作。“非成员不能读取空间详情”是由后端校验的全局业务安全规则。

## 八、邀请码前端状态怎样接入

### 1. 原来代码的职责

`WorkspaceListView.vue` 原来只提供空间创建，邀请码入口处于禁用状态；`WorkspaceOverviewView.vue` 只读取空间详情，没有邀请状态。这个阶段边界保证页面不会在后端接口不存在时伪造加入成功。

### 2. 改动后的职责与数据流

`api/workspace.ts` 新增加入、当前邀请、历史、生成和停用的 HTTP 类型与函数；`stores/workspace.ts` 保存当前邀请及历史，并组合刷新动作；列表页负责输入和路由，概览页只在当前角色为 OWNER 时加载和展示完整邀请码。

```text
用户输入6位代码 → Store.join → POST /api/workspaces/join
→ 后端返回真实空间摘要 → Store刷新列表 → Router进入该空间

OWNER打开概览 → Store.loadInvitations
→ GET current + GET history → 页面分别展示当前明文和无明文历史
```

生成接口带 `currentInvitationId`，这是旧页面状态与数据库当前邀请之间的轻量并发前置条件。创建响应成功后，Store 会立即保存新代码；即使随后历史刷新失败，也不会把一次已经成功的创建误报成失败。停用成功后则立即清空当前代码，避免刷新失败时继续把旧代码显示成可用。

### 3. 权限边界

“概览页只给 OWNER 渲染邀请管理区”是前端体验控制，不能代替安全校验；真正的全局规则由后端再次验证当前用户、成员状态和所有者身份。MEMBER 即使手工调用管理接口也会得到 403，历史响应类型本身不含 `inviteCode`。

## 九、成员页面与危险操作状态

`CODE-005` 新增 `/workspaces/:workspaceId/members`。当前 UI-06 页面并行读取空间详情与有效成员列表，等两者结束后按真实角色渲染；角色和成员数量全部来自后端。MEMBER 可以退出，OWNER 对普通成员可以移除或转让所有权。

退出、移除和转让不会点击一次立即提交。第一次点击只在当前页面展开影响说明，第二次点击带明确动词的确认按钮才调用 API。成功后 Store 使用后端结果刷新空间和成员；退出成功则清除当前空间并回到选择页。这个确认方式只属于当前页面交互，真正禁止 OWNER 直接退出、禁止 MEMBER 移除他人的规则仍由后端保证。

### UI-06 中的保存结果与页面归属

原成员 Store 将 DELETE／转让 POST 与后续 `Promise.all` 读取串在同一失败链里：写入成功后的 GET 报错也会使页面进入“成员操作失败”。现在把事务结果和展示刷新分开；这不是忽略读取错误，Store 仍保存读取错误，页面据此显示“操作已完成，但页面刷新失败”并提供 GET 重试。

```text
确认移除 A 成员 → DELETE 成功 → 本地去除该成员／更新已知计数
  → 重新读取详情与成员（allSettled；详情失败仍保留已知结果）
  → 全成功：正常结果；有失败：保留成功提示、仅允许重新读取

确认转让 → POST 返回新的 OWNER 与当前用户角色
  → 同步当前空间／已有列表／成员角色、清邀请 → 列表与成员 GET

确认退出 → POST 成功 → 清当前空间 → 尝试读空间列表
  → 即使列表失败也返回选择页，不能显示成退出失败
```

设置页沿同一原则：改名使用后端规范化名称同步标题、侧栏和已缓存列表；归档／恢复使用后端返回的状态，空间列表失败单独提示。页面本地的 `pageLoading/pageError` 表示当前页初始化是否完成，不能拿 Store 的公共 `loading/errorMessage` 代替，否则写后列表读取会让当前页消失。名称校验按 Unicode 码点而非 UTF-16 长度计数、去除 Java 空白／分隔符；唯一性最终由服务端和数据库保证。

`beginManagement` 在 Store 开始治理写入时生成版本并使更早 GET 失效；页面卸载的 `invalidateManagement`、换空间的 `clearCurrent`、退出账号的 `clearAll` 使旧回调过期。POST／DELETE 返回后先比较版本，过期就不更新 Store、不发旧空间的新 GET。页面另在每个 await 后检查空间 ID、页面版本、卸载状态，控制局部草稿、确认和导航。这里用两个层次是因为 Store 保护共享数据，页面保护自身交互；只做其中一个不完整。确认保存的是原空间与成员，不会拿切页后的新参数提交。

这些保护只停止旧前端回调。服务器已移除 A 的成员，随后切 B，不会撤销 A 的事务；真正的 OWNER 权限、转让目标仍有效、归档来源与不能直接退出由原后端在请求时校验。复习时可以沿“转让已经提交 → 成员 GET 失败”和“退出响应迟到 → 页面已在 B”各追一次代码；测试通过不代表已经能独立实现。证据和未执行边界见 [UI-06 任务](../specs/003-ui-migration/tasks.md#ui-06-正式迁移2026-10-01)。

### UI-07 中的公开演示与真实入口

`LandingView.vue` 原来负责公开介绍、注册／登录导航及轨道装饰，没有业务读取。此次仍保留公开页职责，按 V2 改为产品说明、局部曲线与观点示意、实际开始流程；不能为了画一条示意曲线就挂载 `StockMarketPanel`。业务面板会读取行情、使用共享 Store 并定时刷新，放到匿名首页会引入访问前置条件和生命周期，而本地 SVG 只需要静态路径。

示意交互的数据流是 `记录按钮 → selectedNote.value → aria-pressed 和单个图中标记高亮`，不调用 API、不发表观点。虚构人物、价格和曲线有邻近标识，实际空间内的数据仍来自成员和行情接口。不要把参考里的营销数字、虚构资产或固定报价写成平台事实；四个数字块因此呈现真实四步流程。

真实入口读取 `authStore.isAuthenticated/isSuperAdmin` 计算同一个 `entry`：匿名去 login，普通账号去 workspaces，管理员去 admin-users。它只决定当前按钮的文字和候选目的地，不证明账号有效。刷新后 Store 恢复的角色可能过时，第一次进入受保护页面时，原守卫用 `/api/auth/me` 确认；例如本地误存普通角色的管理员，确认后仍转治理后台，过期 Token 的 401 则清理会话并去登录页。后端继续对每次业务请求鉴权。这次没有修改认证判断或安全边界。

四个首页区块在首次加载时随组件同步渲染，路由可以按已知 hash 返回元素和 24px 留白；研究时间线要等待接口和图表布局，继续由研究页自行定位。历史返回优先恢复实际滚动位置，即使 URL 有 hash，也不能再次强制定位锚点。浏览器原生的同文档 hash 跳转、RouterLink 导航、直接打开新文档及刷新应分别检查；页面底部还受最大滚动距离限制，验收需要确认目标可见，不能要求无法达到的留白。

走马灯的正常状态保留用户确认的持续滚动；减少动态时只关闭运动还不够，需要隐藏视觉重复、允许第一组换行并收缩，否则内容仍会留在窗口外。局部 CSS 实际曾因 `flex-shrink: 0` 使静态组保持超宽，已改为可收缩的完整列表；浏览器同时检查每项边界和窄屏溢出。证据见 [UI-07 任务](../specs/003-ui-migration/tasks.md#ui-07-正式迁移2026-10-01)。复习时沿一个示意按钮和一个真实入口分别追到状态或后端，解释为何前者不应发请求。

## 十、归档只读、访问失效与退出登录

### 1. 原来的状态处理

空间列表已经能把非活动空间放入“已归档空间”区域，但概览和成员页没有按状态关闭写入口，设置页也不存在。页面捕获空间 API 错误后只展示通用加载失败，无法区分网络暂时失败、成员关系失效和账号失效。新增的退出登录按钮最初只调用 `clearCurrent()`，会清除当前详情，却仍在 Pinia 中保留空间列表缓存。

### 2. 修改后的数据流

```text
OWNER 在设置页二次确认归档
  -> Store 调用 POST /api/workspaces/{id}/archive
  -> 后端返回 ARCHIVED_BY_OWNER 与 archivedAt
  -> Store 使用响应更新当前空间并清空当前邀请码
  -> 概览、成员、设置页显示只读状态

空间 API 返回成员失效/不可见
  -> 清除当前空间 -> 尝试刷新可访问列表 -> 返回 /workspaces 并提示原因

受保护 API 返回 401
  -> 清除 JWT、当前用户与全部空间 Store -> 返回登录页
```

归档后的普通 MEMBER 仍能在成员页退出，这是全局业务规则允许的例外；隐藏 OWNER 的移除和转让按钮只是页面体验控制，后端仍会对手工请求返回 `WORKSPACE_ARCHIVED`。网络错误不会触发清理或跳转，因为“服务器暂时不可达”不能被误判成“用户已经失去权限”。

退出登录属于账号会话边界，因此使用 `clearAll()`，不只清当前空间。它会移除 JWT、当前用户、空间列表、详情、邀请和成员缓存；这和“切换空间”只调用 `clearCurrent()` 的页面行为不同，也不等于退出空间成员关系。

UI-01 将账号区移到底部，但保留完整退出调用链；`auth.logout()` 还负责股票和后台状态，Layout 再清空间。清空缓存只改变当前内存，不能撤销已经发出的请求，因此空间列表、邀请及成员读取以请求版本判断响应归属，`clearCurrent/clearAll` 递增版本，使旧响应无法回填；创建／加入用会话版本阻止旧保存响应恢复账号状态，选择页卸载后也不再跳转。HTTP 错误另判断请求认证头是否属于当前会话，避免上一账号的延迟 401 清除新账号。复现和测试入口见 [BUG-006](bugs/BUG-006-stale-session-response.md)。

空间外壳的 `scoped` 样式限制选择器匹配，不隔离继承的 CSS 变量。UI-01 在 `.research-theme` 内统一覆盖语义颜色，六个旧子页继续继承；模板排版规则只命中外壳与选择页，逐页检查仍不可省略。`RouterView` 以空间 ID 为 key，让只在 mounted 加载的旧子页在换空间时重新创建；同一空间内更换股票仍保留原页面参数监听。把“页面实例是否复用”和“异步响应是否仍属于当前业务对象”分开判断，不能只看标题已变就认定状态正确。具体视觉落点见 [迁移设计](../specs/003-ui-migration/design.md#ui-01-实施落点)。

`CODE-008` 的空间改名展示了另一个状态同步点：设置页提交名称后，`api/workspace.ts` 发送 `PATCH`，Store 使用后端返回的详情更新当前空间，并按 ID 更新选择列表里的名称。页面不在请求前乐观改名；后端会再次核对当前 OWNER、活动状态和全平台名称唯一性。设置页隐藏 MEMBER 和归档空间的表单只是交互提示，不能代替接口权限。浏览器测试在所有权转让后由新 OWNER 改名，再归档和恢复，证明角色变化与页面名称都来自最新业务结果。

`CODE-009` 把个人资料放在 `/profile`，入口不依附空间 ID。昵称提交经 `PATCH /api/auth/me` 返回最新用户 VO，`authStore` 同步 Pinia 与本地展示缓存；密码提交经 `POST /api/auth/password`，只有成功响应才清除当前会话与空间缓存并进入登录页。原密码错误保留当前表单和会话，页面展示后端错误；后端对旧 JWT 的版本校验才是真正的多设备失效边界。

`CODE-210` 让概览页从 `GET /api/workspaces/{workspaceId}/overview` 读取正在关注数量与近期动态。空间身份仍由原有 Store 维护；这份只在概览展示的响应留在页面局部状态，加载失败只让动态区显示重试，不覆盖已经成功读取的空间详情。页面按后端返回的事件类型显示文字并链接到同一空间的研究详情；已撤销观点的倾向和正文在后端就被清空，前端只显示占位，不能靠隐藏 DOM 当作保密措施。

### UI-05 中的独立读取与邀请生命周期

概览有三份不同职责的数据：空间详情说明身份、成员数和归档状态；overview 响应说明正在关注的真实数量与最近动态；邀请接口只服务活动空间 OWNER。页面先重新核对空间详情，再独立并行读取动态和邀请，普通网络失败留在各自区域。动态失败时数量暂不可用，不能把没有取得数据解释成没有关注；MEMBER 不请求完整邀请接口，但页面入口限制仍由后端逐次鉴权兜底。

当前邀请码和生成历史可以部分成功。`Promise.all` 在任一拒绝时不能在原成功赋值位置取得两个结果；改用 `Promise.allSettled` 后，Store 分别更新 fulfilled 的结果，仍抛出失败并设置 invitationError。这样历史读取失败不丢掉已取得的当前码，当前码读取失败也保留已取得的历史。它不是忽略失败，而是保留成功部分并提供只读重试。生成先保存 POST 返回的码、停用先清空成功删除的码，再读取展示数据；读取失败不能把已完成操作误报为提交失败。

`clearInvitations` 对应邀请区域的生命周期：递增邀请读取和写入版本、清理该区域状态，由概览卸载和空间／账号清理调用。旧 POST 返回后先判断版本才允许刷新，旧 DELETE 也先判断再清空代码，避免旧空间回调覆盖新空间。这沿用 [BUG-009](bugs/BUG-009-research-target-lifetime.md) 的写入回调原则；页面还检查卸载状态，防止同一空间离开概览后，旧权限失败改变共享自选导航。

复制沿浏览器 Clipboard API；成功才提示已复制，拒绝则保留可选中的代码并说明手动复制。重新生成请求携带页面所见的 `currentInvitationId`，由后端对照当前记录；另一会话已换码会收到 `INVITATION_CHANGED`，用户重新核对后手动操作，不自动重发 POST。所有权转让后重新进入概览会读取新身份；归档空间保留数量／动态读取，写入权限仍由后端判断。数量与最终验收统一见 [UI-05 任务证据](../specs/003-ui-migration/tasks.md#ui-05-正式迁移2026-10-01)。

### UI-08 中的真实表单与提交生命周期

AuthLayout 原来负责轨道装饰和双区外壳；Login／Register 负责 Element Plus 校验和真实提交；Profile 负责昵称／改密。迁移后外壳采用 V2 顶栏、说明与表单构图，资料页采用分段布局，三个页面仍沿原 API。不能把预览“点击就成功”的脚本放进正式组件，也不能因新按钮样式删掉 label、autocomplete、Enter 或错误反馈。

登录／注册只使用 form submit 触发，取消重复 keyup Enter 入口；submitting 在 await validate 之前锁定，避免校验尚未结束时第二次提交进入。显示密码是原生 checkbox，不提交表单；按钮、输入和 checkbox 在请求期间禁用。校验失败解除锁定，后端错误以局部 alert 展示并保留草稿。注册成功回 login，带 username、registered 原因与本次 redirect；顶栏与表单里的登录／注册切换也保留 redirect，登录成功按原守卫检查角色后回目标，包含 query／hash。

个人资料的 busy 同时约束昵称和密码，避免一边改密清会话、一边继续改昵称。昵称去首尾空白并检查 1～20 字符；新密码仍沿现有 4～64 字符和确认一致，原密码由后端核对。原密码错误不清会话；成功后提示重新登录并预填账号，新资料实例的密码字段为空。昵称响应在 Store 同步共享资料，页面只控制本地输入／反馈；会话与离页保护的完整算法集中在 [认证设计](../architecture/authentication.md#ui-08旧回调与当前会话)，不把页面卸载理解成取消服务器写入。

auth-form.css 只作用于 auth-page；校验文案以正常流换行，320px 下不覆盖下一项。成功 ElMessage 被挂到 body，显式提供 research-theme 变量并恢复 fixed 定位，不能指望页面祖先样式传到它。测试定位由第几个 input 改为明确 label，保留原 auth smoke 断言和 finally 清理。截图与实际行为证据见 [UI-08 任务](../specs/003-ui-migration/tasks.md#ui-08-正式迁移2026-10-01)；可练习解释“为什么在 await validate 前加锁”和“注册切换后 redirect 为何仍存在”，测试通过不替代独立实现。

## 十一、共享自选首个前端闭环

`CODE-204` 把此前只有后端能力的股票搜索和原子添加接入 `/workspaces/:workspaceId/stocks`。后来 CODE-211A 把“选择搜索候选”和“填写初始观点”拆开：页面负责交互，`stock Store` 分别保存列表、搜索、单股行情、图表和提交状态，`stock API` 描述请求契约，后端仍负责空间成员权限和可信字段。

```text
用户输入代码或名称
  -> stock Store.search 调用 GET /api/stocks/search
  -> 每次搜索递增请求版本，只有最新请求可以更新候选、错误和加载状态
  -> 点击候选进入 /workspaces/{workspaceId}/stocks/market/{code}
  -> stock Store.loadMarketDetail 按空间和标准代码读取行情及关注关系
  -> 页面默认只读；已有活动周期时显示研究时间线入口
  -> 用户明确点击加入／重新关注后才展开初始观点表单
  -> stock Store.add 调用 POST /api/workspaces/{id}/stocks
  -> 后端重新取得可信行情并在一个事务中写四类对象
  -> Store 调用 GET /api/workspaces/{id}/stocks 刷新共享列表
  -> 同空间其他成员读取到同一条股票、最近一条未撤回观点和本期统计
```

共享列表只负责扫视和导航：股票名称进入研究详情顶部，观点统计旁的“查看全部观点”带 `#research-timeline` 进入同一页面并直接定位到时间线，列表自身不展开观点正文；“最近一条观点”只描述最近未撤回记录，不能写成空间的统一当前倾向。研究详情的发表表单默认收起，由“发表观点更新”或“开启新一期研究”按需展开；待确认草稿会自动展开。由于时间线依赖异步接口数据，详情在数据渲染完成后主动定位 hash 目标，不能只依赖浏览器初次加载时的原生锚点。观点数和参与成员数说明本期研究活跃度，初始观点、更新、复盘与历史周期由详情页的时间线接口按需读取。页面隐藏归档空间的搜索和提交区只是体验控制，后端拒绝归档写入才是全局安全边界；归档成员仍能读取历史列表。表单中的目标价和止损价为可选正数。Vue 对 `type="number"` 的 `v-model` 可能在运行时给出数字，所以转换函数同时接受字符串和数字：空字符串转 `null`，正数提交，其他值阻止提交。这个问题由真实浏览器而不是类型检查发现，说明静态类型不能替代运行时验收。

研究详情现在先读股票身份、活动周期和作者选项，再按当前筛选从服务端取首批 20 条观点；“加载更早的观点”使用返回的游标继续读取。跨页出现同一周期时合并观点，不重复显示周期卡片；切换作者、倾向或类型会清空旧批次并重新请求，不能把浏览器内的 20 条当成完整筛选范围。发表、撤销、结束或重新关注后重读首批；快速切换股票或筛选时用请求版本忽略旧响应。当前周期操作不依赖历史批次是否加载完。

研究详情的行情区独立读取单股最新可用报价；失败时只显示行情重试，不遮住已经成功读取的研究时间线。报价与活动周期开始价按代码、币种、模拟状态和报价时间检查后才显示未复权价差；没有活动周期或可用报价时保留明确空状态。图表复用共享股票 ID 的 K 线／分时组件，从“查看全部观点”锚点进入时先收起图表，避免图表异步增高把时间线推离定位点。这里的价差只描述两个价格快照，不能解释为含分红或复权的投资收益。

## 十二、按需 K 线与分时图的数据流

最初共享自选页只展示添加时保存的报价快照，它适合回答“开始关注时多少钱”，不能回答“后来怎样变化”。当前页面增加的是动态查询视图，不改变研究事务里的不可变快照；未关注股票和已关注股票复用同一图表组件，但读取身份不同：

```text
用户从搜索结果打开未关注股票
  -> 行情详情使用 workspaceId + code 校验成员和可信目录身份
  -> 查看不会创建 workspace_stock、research_cycle 或 stock_opinion

用户展开一只已加入股票，或打开上述独立行情详情
  -> 默认只请求当前可见股票最近 1000 根日 K
  -> 切换周期时替换当前 K 线序列
  -> 拖到最左侧时带 nextBefore 请求更早一批
  -> Store 按时间去重并插到同一数组，图表保持原可见位置

用户切换到分时
  -> 当天走 /intraday，历史日期由后端用 1 分钟 K 线重建
  -> 响应携带市场时区和常规交易时段，组件据此生成完整分钟横轴
  -> 已返回的点按 HH:mm 落位，尚未来到的分钟保留 null，所以盘中曲线只画到当前位置
  -> 午休时段压缩为一个边界标签，折线跨缺失的边界分钟连接，但不会越过最后一个已知点
  -> 只有面板展开、页面可见且后端标为 updating 时每 30 秒刷新
  -> 切回 K 线、折叠或后端返回非更新状态后不再访问上游
```

K 线和分时使用两组 Store 状态，是因为它们的加载、错误和刷新生命周期不同。`candlestickSeries` 还需要 `hasMore/nextBefore` 与“加载更早数据”错误；`intradaySeries` 需要日期和 `updating`。把两者挤进一个通用 `chartData` 会让一次分时刷新覆盖 K 线分页状态，也难以区分首次加载失败和后台刷新失败。

当前股票目录只支持 A 股和港股，K 线按这两个市场常用的“红涨绿跌”显示：ECharts 的 `color/borderColor` 对应收盘价不低于开盘价，使用红色；`color0/borderColor0` 对应收盘价低于开盘价，使用绿色。上游接口只返回开高低收数值，不返回展示颜色。每根 K 线响应同时已有 `volume`，组件在主图下方使用同一时间轴和缩放范围绘制中性灰色成交量柱，不为成交量附加未经接口提供的涨跌方向。这个约定属于当前受支持市场的前端展示规则；如果以后真正支持美股，应根据市场显式选择配色，不能直接反转所有市场，也不能用颜色代替数值、正负号和 K 线形态。

这些数组当前只存在浏览器 Pinia；刷新页面后重新从项目 API 读取。后端已有 Redis 共享缓存与原进程内短缓存，但动态序列仍不写入 MySQL，具体机制见 [缓存设计](../specs/002-stock-research/design.md#46-redis-共享行情缓存与访问保护)。搜索候选不会触发图表请求，所以模糊搜索不会消耗历史 K 线不同标的额度。Redis 接入前，真实浏览器已验证日 K、1 分钟 K、当天／历史分时 canvas、供应商分钟范围提示及休市日提示，用户也实测左拖可逐批看到 1990 年代日 K；这些历史证据不能代替 Redis 接入后的页面验收，详见 [阶段任务](../specs/002-stock-research/tasks.md)。近一年日期由官方交易日日历判断，当天返回点按市场时区过滤，不能再把供应商上一交易日数据错标为今天。

历史分时与当天分时的均价来源不同：当天接口直接提供 `avg_price`；历史日期由分钟 K 线重建。A 股 K 线的成交量以“手”为单位，后端必须先按每手 100 股换算，再使用累计成交额／累计股数计算均价，否则错误均价会放大约 100 倍，把正常价格线压在纵轴底部，看起来像没有数据。这个单位规则属于 A 股历史分时转换，不能扩大到港股。

分时图右轴的百分比不是独立的业务数据，而是左轴价格相对 `referencePrice`（上一交易日收盘价）的另一种刻度表达。组件从已加载价格与均价的最大偏离选择对称百分比档位，再反推左轴价格上下界；左右轴共用四个分段，保证每一条水平网格线上的价格和百分比相互对应。动态分档比完全固定 `±10%` 更能看清小波动，又比每次按精确极值缩放更稳定。为了让 Tooltip 显示“涨跌幅”，前端会生成一组仅用于提示的透明辅助序列，但它仍由当分钟价格和 `referencePrice` 现算，不是后端新增的第三套价格数据。小数位限制也只在显示格式化层执行。

分时价格线使用蓝灰色，均价线使用琥珀色，成交量柱使用中性灰色。价格线和成交量柱本身不表达上涨或下跌方向，因此不使用 K 线的红绿语义色；实际涨跌仍由昨收基准、右轴百分比、正负号和 Tooltip 数值表达。

### UI-02 中的异步生命周期检查

共享自选的模板负责标题、统计条、搜索结果、股票卡片与历史入口，Store 负责接口状态；关注价格、最新个人观点和周期统计分别使用已有 VO 字段，不在重排时混成实时价格或团队结论。后端周期总数包含撤回记录占位，但最近观点只选择未撤回记录，所以不能只按当前可见正文计算总数。

搜索页从行情页返回会重新创建，但只更换 URL 的 `q` 时 Vue 可以复用页面。因此共享自选既在初次读取后恢复参数，也监听 `q`，并在离页清理搜索与请求版本。这种区别可以解释“地址已变而数据没变”的问题。

原位图表切换先清空展开 ID，经过一个 `nextTick` 完成旧面板卸载，再创建新面板；否则 Vue 更新多张卡片的顺序可能使旧面板清空新面板共用的数据。定时器清理还需要配合请求版本：卸载不能取消已经进入 `await` 的回调，回调恢复后必须确认自己仍属于当前面板和模式，才允许调度下一次刷新。修复证据见 [BUG-007](bugs/BUG-007-market-panel-delayed-refresh.md)。UI-02 完成生命周期修复，共用图表的视觉随后在 UI-03 迁移。

### UI-03 中的图表主题与提交边界

Vue 模板负责股票身份、报价、表单和工具栏，`StockMarketPanel` 负责当前图表模式、日期、读取及刷新调度；两个 ECharts 组件只把已有序列画出来，不访问后端、不决定是否允许加入研究。因此图表配色放在 `market-chart-theme.ts`，业务限制仍留行情页和后端。这次没有为手机复制图表实例，而是调整同一画布与坐标边距；ECharts 的窄屏 media 之外也提供默认配置，使宽度恢复后恢复宽屏边距。

普通元素可继承 CSS 变量，但 Canvas 已画出的像素和挂到 `body` 的 Tooltip 不会随着组件的 scoped 样式自动改变。主题函数通过 `getComputedStyle(host)` 读取宿主变量，再显式传给 ECharts。这个做法让坐标字体、底色和提示框与空间主题一致，同时保留红涨绿跌、价格／均价、百分比和成交量的原含义。

初始观点表单只发出用户可编辑的草稿，关注开始价仍由后端重新获取。提交时锁定表单并防止重复发出事件；提交失败保留草稿。页面版本与 Store 请求版本分别保护导航和接口状态，不能因为旧 POST 返回就跳回上一只股票。跨页的保存结果还要和读取错误分开处理：已保存的提示曾在研究页初始化时被清掉，完整复盘见 [BUG-008](bugs/BUG-008-saved-result-lost-on-navigation.md)。学习时沿“表单事件 → 页面 → Store → API → 后端事务 → 刷新 → 导航”解释，不能仅按文件名逐个背代码。

### UI-04 中的业务目标与异步回调

研究详情不是一个接口结果直接填满整页：`WorkspaceStockResearchView` 从路由取得空间／共享股票 ID，Store 读取当前周期摘要，时间线接口按筛选和 cursor 返回历史分批数据，报价另按可信 code 独立读取。页面以周期 ID 合并各批、以观点 ID 去重；当前周期用于写入，历史周期用于追溯，报价用于价格快照比较，三者不能互相代替。

用户展开表单时记录当前周期 ID，发表时携带该 ID；结束确认也绑定原周期。若别人已结束并重开，后端先拒绝旧目标，用户重新读取后还要明确确认草稿适用的新周期。这避免标题和当前周期更新了，原草稿却被静默提交到另一期。换股票则清理这些状态，不把 A 的草稿／确认区带到 B。

版本保护需要覆盖每个异步阶段。已有读取版本能拒绝旧 GET，但旧 POST 如果在切到 B 之后才返回，并再次启动 A 的 GET，这个 GET 会成为“最新请求”。因此 Store 另有写入版本，清理时使旧写入回调失效；页面同时检查目标与版本，防止写后时间线等待结束时把 A 的提示显示到 B。失效不撤销服务器事务，完整分析见 [BUG-009](bugs/BUG-009-research-target-lifetime.md)。

保存结果与刷新结果分别表达。时间线读取函数内部捕获错误时返回 false，让调用者保留“已经保存，但时间线刷新失败”；若只吞掉异常返回 undefined，外层就无法准确判断刷新是否完成。重试沿原 GET 链读取，不重复 POST；先前已读的更早记录加载失败仍保留在页面。研究页的异步锚点由页面定位，路由只对该锚点让出滚动控制，其他页面继续保留浏览器历史位置。

## 十三、超级管理员治理入口

`CODE-007` 没有把管理按钮塞进普通空间页面，而是新增独立 `/admin/users`、`/admin/workspaces` 和 `/admin/operation-logs`。登录和 `/api/auth/me` 返回 `accountType`，Pinia 保存它，路由守卫据此把 `SUPER_ADMIN` 导向治理区、把普通账号导向空间区；这只是导航分流，真正的管理员身份仍由后端每次请求查询 `super_admin` 表确认。

```text
管理员登录
  -> auth Store 保存 accountType = SUPER_ADMIN
  -> 路由守卫进入 /admin/users
  -> admin Store 调用 /api/admin/users 等治理接口
  -> 列表只展示治理摘要，选中目标后再读取详情
  -> 禁用用户或归档空间先展开影响说明和二次确认
  -> 后端提交目标状态与 SUCCESS 日志，响应最新详情
  -> Store 刷新当前详情、列表和操作记录
```

用户详情显示其空间成员关系；禁用前提示会影响哪些活动空间和由其拥有的空间，但禁用不会删除成员关系或自动转让所有权。空间详情只显示名称、状态、所有者和成员身份，不读取股票、观点、完整邀请码等业务内容。OWNER 自己归档的空间不能由管理员覆盖恢复；管理员只能恢复 `ARCHIVED_BY_SUPER_ADMIN`。这些页面限制用于让操作含义清楚，手工请求仍必须经过后端同样的状态与身份校验。
