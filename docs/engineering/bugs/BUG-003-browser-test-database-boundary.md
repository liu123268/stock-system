# BUG-003：浏览器测试写入开发库

更新时间：2026-09-04

## 1. 现象与影响

隔离测试库 `stock_system_test` 为空，但开发库 `stock_system` 出现了命名为 `browser_o_mtmk4orf` 的自动化账号、`浏览器空间mtmk4orf` 和对应成员关系。创建时间与浏览器测试命名规则吻合，说明一次真实浏览器测试把数据写进了开发库。

这不是“测试库应该有数据却没有”的问题。测试成功后测试库为空通常意味着事务回滚或清理成功；真正的缺陷是自动化数据越过边界进入了需要保留用户数据的开发库。

## 2. 原来的数据流

```text
浏览器脚本 -> BACKEND_URL 指向的现有后端 -> 后端实际数据库未知
      └----> 清理函数读取 application-test.properties -> stock_system_test
```

脚本只证明“清理函数准备操作测试库”，没有证明“接受注册和建空间请求的后端也连接测试库”。如果 8082 上恰好是日常开发后端，写入发生在 `stock_system`，最后清理却查询 `stock_system_test`，于是清理显示成功而开发库留下测试数据。

人工查看启动日志也是流程要求，但它不是程序能够强制执行的条件，因此仍可能被遗漏。

## 3. 根因

- 开发库地址曾直接放在公共 `application.properties` 中；`spring-boot:run` 激活 test profile 时，测试资源配置不一定进入运行时类路径。
- 开发与浏览器测试默认共用 8082/8083，测试脚本可能复用一个已经存在的开发后端。
- 浏览器脚本只校验清理目标库，没有从运行中的后端读取实际 JDBC catalog。
- 规则停留在文档和人工日志核对，没有变成写入前必经的代码闸门。

## 4. 修复

1. 公共配置只保留共享项，数据库 URL 分别进入 `application-dev.properties` 和 `application-test.properties`；两者都在主运行时资源目录。
2. `start-dev.cmd` 显式使用 dev profile 和 8082/8083；新增 `start-test.cmd`，显式使用 test profile 和 18082/18083。
3. `TestDatabaseSafetyGuard` 只在 test profile 激活，启动时从 DataSource 真实连接读取 catalog；不是精确的 `stock_system_test` 就终止启动。
4. `/api/test/environment` 只在 test profile 注册，返回运行后端的 profile 与真实 catalog。
5. 浏览器脚本在注册账号之前必须调用该接口并得到 `test + stock_system_test`；开发后端不存在该接口，所以配置错端口时会在任何业务写入之前失败。
6. 清理顺序扩展到观点、研究周期和空间股票，再清理邀请、成员、空间与账号。

## 5. 数据处理与验证

- 精确核对残留账号 ID 2、空间 ID 1、成员关系 ID 1；未发现邀请、股票研究或超级管理员关联。
- 只删除上述自动化账号、空间和成员关系；正常账号 `liul` 保持存在。
- 清理后开发库自动化前缀账号、空间均为 0。
- 后端全量 37 项测试通过，Flyway 日志显示连接 `stock_system_test`；新增测试同时证明错误连接开发库会被 guard 拒绝、环境接口返回真实测试库。
- 测试后核对测试库用户、空间、空间股票、研究周期和观点均为 0；前端静态检查通过。

## 6. 预防规则

现行执行要求统一见 [测试规则](../testing.md#4-测试数据清理)。本复盘保留当时为何误写以及如何修复的证据，不维护第二套检查步骤。

## 7. 面试转化

这个问题可以用于回答“如何避免自动化测试污染真实数据”。重点不是说使用了 test profile，而是解释三层保护：独立配置和端口降低误操作，后端启动 guard 验证实际 JDBC catalog，浏览器在首个写请求前通过 test-only 接口再次验证运行中后端。最后再用唯一标识和精确清理处理测试中断后的残留。
