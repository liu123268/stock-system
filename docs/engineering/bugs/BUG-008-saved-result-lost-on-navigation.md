# BUG-008：进入研究页后丢失已保存提示

状态：2026-09-30，在 UI-03 真实浏览器验收中复现并修复。

## 现象与影响

用户在独立行情页提交初始观点。POST 已成功，随后用于刷新共享自选的 GET 失败，Store 已设置“研究已经保存”的提示；页面继续用成功响应里的业务 ID 进入研究详情。如果研究详情 GET 也失败，旧代码只显示“研究记录暂时无法加载”，丢失先前的保存结果。用户可能误以为提交失败，再次填写、提交。

这不是数据库保存失败，也不是 Vue 模板少写了一条提示。详情页本来就能显示“操作已经保存，页面暂未刷新”，但它依赖的状态在初始化时被清除了。

## 排查与根因

先沿完整链路定位：`StockInitialOpinionForm` 发出草稿 → 行情页调用 `stockStore.add` → 后端原子写入成功 → Store 使用 `Promise.allSettled` 刷新列表／历史，失败设置 `refreshWarning` → 行情页根据成功响应跳转 → 研究页 `load()` 初始化清除 `refreshWarning` → 详情读取失败。

前一个页面正确区分了写入与读取，但下一个页面将该提示当作可直接清掉的旧页面状态。跨页导航没有撤销服务器事务，却丢掉了浏览器用来解释事务结果的信息。

## 修复及边界

研究页首次进入时暂存已有保存提示，读取失败后恢复；成功取得详情则正常展示。仅首次进入承接保存结果，后续只更换股票或空间参数，不沿用上一目标的保存提示。已有 `retryResearchData` 只读取详情、时间线、共享列表与历史，无需新建提交接口或重做研究页排版。

同时，行情页加载／提交回调检查页面版本和卸载状态，Store 的初始观点提交版本在行情清理时失效。这能阻止旧提交响应在用户切股票后刷新旧目标或导航回旧研究页，但不能撤销已经在后端成功的写入；用户再次查看原股票时仍会读到该记录。

## 验证

`frontend/e2e/ui-market-smoke.mjs` 连接真实 test 后端和 MySQL。拦截器先执行真实 POST，再让后续列表与详情 GET 返回 503；页面显示已保存提示，相关研究数据三条已存在。解除读取失败后点击重新加载，详情恢复，POST 计数始终为 1。另一用例延迟真实 POST 响应，切到第二只股票再放行，页面仍属于第二只股票；表单提交期间不可编辑／取消，重复点击没有第二次 POST。Store 单元测试另验证离页后迟到提交不调用列表／历史读取。

验收数量、截图、测试数据和进程清理的唯一记录见 [SPEC-003 UI-03](../../specs/003-ui-migration/tasks.md#ui-03-正式迁移2026-09-30)。

## 预防与面试表达

检查保存流程时，应沿着“写入 → 刷新 → 导航 → 新页面初始化 → 失败重试”看完，不能只检查提交函数。清理状态前要区分旧目标的数据与用户刚完成操作的结果。测试规则及迁移要求见 [测试规则](../testing.md) 和 [开工前复核](../../specs/003-ui-migration/design.md#2026-09-30-开工前复核容易遗漏的行为约束)。

可以这样解释：POST 成功代表事务已提交，后续 GET 失败只代表当前页面尚未取得新数据。前端必须保留这个区别，给出只读重试；请求版本解决旧回调归属问题，不能用来声称服务器写入已经取消。
