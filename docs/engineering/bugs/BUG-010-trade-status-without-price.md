# BUG-010：无价格时丢失交易状态与旧状态冒充当前核实

状态：2026-10-08 修复并随每日状态查询功能验证；实际覆盖和生产发布证据见 [CODE-206J](../../specs/002-stock-research/tasks.md#code-206j每日交易状态核实2026-10-08)。

## 现象与根因

真实长桥样本 `03333.HK` 明确返回 `Delisted`，同时最后价格不可用，最后成交时间是 1970 年。旧 SDK／CLI 适配器和 provider 以“价格正数且有有效时间”筛选整条证券结果，这会连同有效交易状态一起丢弃。旧目录仅保存 `listing_status`，没有状态何时成功核实和何时查询失败，无法分辨“过去正常”与“本次确认正常”。

价格、交易状态和股票身份属于不同事实。旧 K 线只说明最后取得的成交数据日期，不证明停牌或退市；查询失败也不等于退市。把一个字段不可用扩大成整条记录不可用，会丢掉供应商已经明确给出的信息。

## 修复与数据流

SDK／CLI 先保留请求代码对应的证券结果，再分别处理：可识别的 `trade_status` 交给 [StockStatusChecks](../../../src/main/java/com/stock/system/stock/market/StockStatusChecks.java) 保存；可用价格与成交时间才进入报价展示。后端每天批量查询和用户按需查询共用这条路径，细节见 [状态设计](../../specs/002-stock-research/design.md#每日交易状态查询2026-10-08)。

`status_checked_at` 表示最后一次明确状态的获取时间；`status_attempted_at` 表示最后尝试，失败只改后者。缓存沿用原始获取时间，不能每次命中就改成“刚刚核实”。数据库的条件更新拒绝早于最后尝试的结果，所以旧缓存或慢请求不能把新退市覆盖为正常；开启新研究时还在股票行锁内重验状态。

页面分别显示当前状态、上次确认、报价时间与最新 K 线日期。确认退市保留股票身份和已有研究，不能新开研究；缺失结果或过期显示待核实。字段与各类时间规则的唯一正文见 [需求](../../specs/002-stock-research/requirements.md#2026-10-08-每日交易状态核实)。

## 验证与预防

SDK 对象替身、CLI 假进程证明无价格状态能解析；真实 MySQL 集成测试证明成功、失败、复牌和旧响应竞争的写入规则。真实 SDK quote-only 探测确认正常／停牌／退市以及缺失结果，混合批次缺失证券不影响有效证券。真实 Chrome 验证无报价的状态、最后确认与历史 K 线日期，图表数据受控；测试 finally 清理为零。正常开发和生产的首次全目录查询另已完成，不能把替身测试当作供应商全覆盖证据。

预防原则：按每个事实自身的有效条件处理，并保存能说明时效的来源时间；不要根据一个字段缺失丢弃整条对象，也不要根据网络失败推断业务状态。验证流程和隔离要求只见 [测试规则](../testing.md)。

## 面试转化

外部 API 一次响应可能包含多个彼此独立的事实；业务状态、价格和历史数据要分别校验。数据库条件更新处理旧响应竞争，字段所有权保护身份和研究历史，时间记录让失败与过期可解释。简洁回答见 [PROJECT-08](../../career/interview/01-project-engineering.md#project-08为什么交易状态不能依赖价格或旧-k-线判断)。
