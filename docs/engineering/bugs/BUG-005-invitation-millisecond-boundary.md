# BUG-005：同毫秒的新邀请码被误判为旧码

状态：已解决  
发现并修复：2026-09-16

## 现象与影响

OWNER 移除成员后立即生成新邀请码时，被移除成员偶发收到 `REMOVED_MEMBER_REQUIRES_NEW_INVITATION`。旧码拒绝正常，但刚生成的新码也可能无法重新加入。

影响范围只在“被移除成员使用移除后新码重新加入”；主动退出者重入、首次加入和已是有效成员重复使用邀请码不依赖这条时间边界。

## 排查

后端完整回归在 `WorkspaceIntegrationTest.shouldRemoveMemberRejectOldInvitationAndAllowANewInvitation` 中复现：请求顺序明确是移除成功后再生成新邀请，但响应仍为 403。业务判断要求 `workspace_invitation.created_at` 严格晚于 `workspace_member.last_inactive_at`，两个数据库字段都是 `DATETIME(3)`。

## 根因

Java 的两次 `LocalDateTime.now()` 有更高精度，但 MySQL `DATETIME(3)` 只保存毫秒。移除与生成发生在同一毫秒时，持久化后的两个值相等，原有严格 `isAfter` 判断无法看见真实先后顺序。

不能把规则改成“大于等于”：移除前已存在的旧邀请也可能和移除时间落在同一毫秒，放宽比较会让旧码越过移除边界。

## 修复

生成邀请前已经锁定空间行。事务在这个锁内查询该空间当前 `REMOVED` 成员最晚的 `last_inactive_at`，先把当前时间截断到数据库相同的毫秒精度；若候选时间没有严格更晚，就将新邀请的 `created_at` 推进 1 毫秒。并发移除与生成仍按空间行串行，不会在查询后插入一个未纳入判断的新移除时间。

加入判断继续使用严格“大于”，因此旧码保持拒绝，新码稳定允许。

## 验证与预防

集成测试把旧邀请创建时间明确设置为等于移除时间，证明等值旧码仍返回 403；随后断言新邀请创建时间严格晚于移除时间，并完成重新加入。详细执行结果见 [SPEC-001 任务证据](../../specs/001-workspace/tasks.md)。

以后用低精度时间字段表达安全或权限顺序时，必须同时设计同精度边界测试；不能只依赖本机调用的自然时间差，也不能用放宽比较掩盖顺序丢失。
