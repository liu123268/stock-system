# BUG-009：研究页切换目标后，旧写入回调仍可能刷新旧股票

状态：2026-09-30，UI-04 源码复核识别生命周期缺口，定向修复后以延迟响应单元测试与真实浏览器验证。没有单独在原版本浏览器重演全部竞态，不把源码推演写成原版本已复现的结果。

## 现象与影响范围

同一空间的研究路由只更换共享股票参数时，Vue 会复用页面实例。原参数监听重读数据，但没有同步清除草稿和结束确认；Store 的观点／结束／撤销 POST 返回后也会直接调用原股票的读取。若 A 的写入响应慢、B 已加载，旧回调仍有机会用 A 数据覆盖 B，或将 A 的操作提示放到 B。周期被其他成员结束并重开时，旧草稿和确认也不能自动代表新周期。

## 排查与根因

沿路由监听 → 页面表单 → Store 写入 → 后端事务 → 读取刷新追踪，发现读取版本只保护已发出的 GET，未保护触发 GET 的旧 POST。顺序是：提交 A → 切 B 并读完 → A POST 返回 → 发出新的 A GET。最后一个读取的版本反而更新，所以单靠读取版本不能判断业务目标是否过期。另一个等待点是写入成功后的时间线读取：它能返回“旧目标已失效”，页面仍必须在显示提示前再次检查目标。

页面参数、共享股票 ID 与研究周期 ID 是不同层次的身份。标题已变为 B 不代表草稿、确认和共享 Store 都已属于 B；同一股票的新周期也不能继承用户对旧周期的确认。

## 修复

`WorkspaceStockResearchView` 在换参数／卸载时使页面版本失效，清空本地草稿、确认、筛选和提示。所有异步阶段完成后先核对空间、共享股票和版本，再操作 DOM、导航或反馈；包括写后时间线等待。表单和结束确认分别保存周期 ID，刷新后目标变化需再次确认，提交期间锁定操作。

`stock.ts` 新增研究写入版本，`clearResearchView` 同时使研究写入和初始观点提交回调失效。旧响应不发起刷新、不修改新目标错误／忙状态；已经保存的观点仍返回成功数据。服务器已成功的写入不会因前端失效而回滚，离页后再次访问原股票仍能读取。权限、活动周期一致性与撤销资格继续由原后端判断。

## 验证与预防

Store 定向测试延迟观点、结束和撤销响应，清理后加载 B，再释放 A，断言没有旧目标刷新、B 保持不变、新状态不被旧回调结束。真实 test 后端／MySQL 的浏览器流程延迟成功 POST 后切 B，验证表单清空、只发一次 POST、共享详情仍为 B；另延迟写后时间线，再切 B，验证无 A 数据和成功／失败提示。双成员流程验证旧周期提交被拒绝、草稿保留、重读后须确认当前周期才手动发表，旧结束确认不结束新周期。

## 面试转化

请求版本不是天然的业务隔离。要分别说明“这个读取能否回填”“这个写入回调能否再启动刷新”“这个确认是否仍指向原周期”；取消前端后续行为与撤销后端事务也必须分开。工程数据流提纲见 [前端工程](../frontend.md#ui-04-中的业务目标与异步回调)。
