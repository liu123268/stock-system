# ADR-001：采用模块化单体而不是微服务

状态：已确认

日期：2026-08-29  
最后补充：2026-09-03

## 背景

项目需要覆盖用户认证、研究空间、共享自选股、行情和成员观点，并承担 Java 实习项目的学习与展示目标。技术路线中还计划评估 Redis、消息队列和可观测性，因此需要明确是否从一开始拆成微服务。

## 决定

当前采用前后端分离的模块化单体后端。所有后端模块在同一个 Spring Boot 应用和 Maven 构建中运行，共用一个标准 `src/main/java`，通过 `auth`、`user`、`workspace`、`admin` 等业务包组织；每个业务包内部再按需要设置 Controller、Service、Mapper、Entity、DTO 和 VO。`common`、`config`、`security` 只承载真正跨业务的基础职责。

当前不拆 Maven 多模块，也不提前拆成 Spring Cloud 微服务。业务模块之间优先通过 Service 或明确公开接口调用，禁止 Controller 互调、随意跨模块访问 Mapper 和循环依赖。目录规则先靠包结构、代码审查和测试执行，不因为采用模块化单体就立即引入 Spring Modulith 或 ArchUnit。

## 原因

- 当前没有多个团队需要独立开发和发布；
- 研究空间、自选股和初始观点包含强事务关系，单体事务更直接；
- 当前没有独立扩缩容和故障隔离的容量证据；
- 单体更适合先完成可运行、可测试、可解释的业务闭环；
- 按业务模块聚合后，完成一个功能时相关 Controller、Service、Mapper 和契约位于相邻目录，比全项目横向堆放更容易维护；
- Redis、消息队列等能力仍可以在模块化单体中学习并验证，不要求先拆服务。

## 备选方案

### 从一开始使用 Spring Cloud

可以展示服务注册、网关和远程调用，但会增加部署、分布式事务、链路追踪和故障排查成本，当前业务无法证明这些成本必要。

### 无模块边界的传统单体

开发初期简单，但业务增长后容易出现跨层调用和职责混乱，因此也不采用。

### 单工程内全局横向技术分层

所有 Controller、Service 和 Mapper 分别放在全局目录中，少量代码时直观，但空间、用户、治理、股票和观点增加后，同一业务会散落在多个远距离目录中。现有认证代码采用过这种结构，阶段 1 开始时按小步迁移到业务模块，避免一次性大搬家。

### Maven 多模块

每个子模块拥有自己的 `pom.xml` 和源码目录，适合存在独立构建产物、依赖隔离或团队所有权时使用。当前项目只有一个部署单元，多模块只会增加 POM、依赖顺序和跨模块事务理解成本，因此不采用。

## 代价

- 所有模块暂时共享一个部署单元；
- 单个模块不能独立扩缩容；
- 业务包内部仍有技术分层，目录比纯横向结构稍深；
- Java 的 `public` 可见性本身不能完全阻止错误跨模块依赖，需要通过评审和测试保持边界；
- 如果未来确实需要拆分，必须先整理模块依赖和数据所有权。

## 重新评估条件

出现以下任一真实条件时再评估服务拆分：

- 某个模块需要独立部署或扩缩容；
- 出现明确的团队所有权边界；
- 单体发布节奏成为可测量瓶颈；
- 行情同步等模块需要与核心业务进行明确故障隔离。

如果只是包边界逐渐被破坏，但仍不需要独立部署，优先评估 Spring Modulith 或 ArchUnit 的结构验证，而不是直接拆微服务。
