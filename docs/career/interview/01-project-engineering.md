## PROJECT-01：为什么采用前后端分离？

### 项目场景

项目需要共享自选股、成员观点、状态管理和后续走势图等交互，旧 Spring 静态 HTML 难以继续维护。

### 完整回答

> 项目前端采用 Vue 3 独立工程，后端使用 Spring Boot 提供 REST API。开发阶段由 Vite 代理转发 `/api` 到后端，前端交互和后端业务可以独立开发、测试和构建。生产已由 Nginx 托管构建文件、统一 HTTPS 入口并反向代理 API，所以开发时的两个端口不会暴露给最终用户。代价是需要维护接口契约、前端状态和独立构建流程，但项目复杂度已经超过简单服务端页面，收益大于成本。

### 项目证据

- `frontend` 独立 Vue/Vite 工程；
- Spring Boot 只提供 `/api`；
- `vite.config.ts` 开发代理；
- 前后端分别具备测试和构建命令。
- 开发端口只见 [开发环境](../../engineering/development.md)，生产结构与验证入口见 [部署说明](../../engineering/deployment.md)。

## PROJECT-02：AI生成代码后如何保证质量？

### 完整回答

> AI用于提高实现和检索速度，但每项改动按风险选择需求检查、代码审查与相应层次的验证，纵向闭环和阶段收尾再扩大测试。项目曾遇到 Vue 脚手架生成的 Oxlint 版本冲突，没有使用 `--force` 掩盖问题，而是核对依赖关系、调整配套版本并重新验证。AI按变化更新唯一文档落点，里程碑再整理面试材料，使下一次对话能继续。候选人的价值不是“会让AI生成代码”，而是能判断正确性、定位问题、验证结果并解释技术权衡。

## PROJECT-03：为什么正式业务页面不能把 Mock 数据当成真实数据？

### 项目场景

项目从认证空状态逐步演进到真实空间、共享自选和股票目录。不同阶段都有尚未接通的下游数据，如果用固定股票或模拟价格填补，页面虽然看起来完整，却会让用户和测试误判系统已经具备真实能力。

### 完整回答

> 项目早期只有认证能力时，工作台只展示真实用户和空状态，没有用固定股票、价格或成员数伪装后端结果。后来空间和共享自选逐步接通，页面只展示真实 API 返回的数据。在首次接入真实股票目录的阶段，开发环境改为查询 MySQL；当时真实报价源还没有完成验证，所以接口主动把价格和行情时间返回为空，页面明确显示“暂无报价”，后端也拒绝用 Mock 价格创建研究周期。Mock 只保留给自动化测试和显式模拟模式。这个做法牺牲了一点页面的“完整感”，但保证了数据来源可信，也让每个阶段的测试能够准确证明系统实际拥有的能力。

### 项目证据

- 旧 `/workspace` 只保留兼容跳转，真实空间入口为 `/workspaces`；
- 当前用户来自 `/api/auth/me`；
- 空间列表、详情和共享自选来自真实 API，股票搜索在开发模式读取 MySQL 目录；
- `DirectoryMarketDataProvider` 在真实报价未接入时返回空结果，页面显示“暂无报价”，添加接口返回受控失败；
- `application-test.properties` 固定使用 Mock，开发环境只有显式选择模拟模式才使用 Mock；
- 真实 Chrome 已从注册、登录、创建空间和进入概览继续验证到双账号邀请加入、退出、重新加入、移除和所有权转让；历史污染和后续修复见 [BUG-003](../../engineering/bugs/BUG-003-browser-test-database-boundary.md)，不能笼统声称早期每轮都没有残留。

## PROJECT-04：为什么用 Spring Boot 管理官方 CLI sidecar，而不是每次行情都执行一条命令？

### 项目场景

历史背景：2026-09 CLI 已能读取真实行情，但 Java SDK 浏览器 OAuth 在本机没有跑通，因此选择 sidecar。本地现已改用独立账号的官方 SDK OAuth，云端保持 CLI；授权、四类行情 SDK 探测和本地登录后网页已通过，证据见 SPEC-002 的 CODE-206I。项目既不能把凭据交给前端，也不能每查一次价格就新建一个 CLI 进程和行情连接。

### 完整回答

> 我把供应商传输细节隔离在 `LongbridgeJsonRpcClient` 后，由 Spring Boot 按需启动并独占一个 `longbridge serve` 子进程。页面仍只调用项目 API；Java 只允许报价、最近 K 线、历史 K 线、当天分时和交易日历五个固定只读方法，通过递增 ID 对应乱序响应，并统一处理限流、短缓存、超时、进程退出和关闭。这样复用了官方 CLI 已经完成的认证和长连接，又没有读取它的私有 Token 文件。代价是部署机必须额外安装 CLI、授权必须属于运行 Spring Boot 的同一系统账号，而且同一 Longbridge 账号不能简单水平启动多个行情副本。这个方案是供应商适配层的实现选择。现在缓存层依赖 `LongbridgeUpstreamGateway`，dev 可选择 `LongbridgeSdkClient`，prod 保留 `LongbridgeJsonRpcClient`；替换传输不需要改业务 API。本地已通过官方 SDK 授权和真实行情探测；登录后的网页已通过，真实到期自动刷新仍待验收。

### 项目证据

- `LongbridgeJsonRpcClient` 只开放报价、最近 K 线、历史 K 线、当天分时和交易日历五个方法；
- 客户端仍保留进程内短缓存与限流；其外已增加可配置的 `CachingLongbridgeMarketGateway` 共享缓存装饰层，机制和边界见 [行情缓存设计](../../specs/002-stock-research/design.md#46-redis-共享行情缓存与访问保护)。这不改变 CLI 子进程与账号连接的部署约束；
- 普通回归使用假 sidecar，不依赖真实账号；真实探测显式启用并精确核对进程退出；
- 完整取舍、部署代价和重新评估条件见 [ADR-002](../../architecture/decisions/ADR-002-longbridge-cli-sidecar.md)。

## PROJECT-05：为什么行情缓存使用自写 Redis 锁而没有接入 Redisson？

### 项目场景

同一行情 Key 未命中时，并发请求若全部回源，会消耗 Longbridge 的调用额度。

### 完整回答

> 项目先在同一 Java 进程内合并相同 Key 的请求，再用带 TTL 的 Redis 锁协调连接同一 Redis 实例的多个进程。取得锁的请求二次检查缓存，仍未命中才回源；未取得锁的请求最多等待 800 毫秒，超时允许受控回源；解锁用 Lua 比对 owner 后删除，避免旧请求误删新锁。目前只有这一种只读行情的限时协调用途，Spring Data Redis 已覆盖所需操作，因此没有引入 Redisson。代价是自己维护锁协议；锁到期、Redis 故障或等待超时仍可能重复请求，单 Redis 实例也没有多节点仲裁或故障切换保证，不能说成全局严格执行一次，更没有证据说自写锁更快。如果以后锁要保护不可重复的业务写入或任务耗时难预测，我会重新评估 Redisson，并同时设计业务幂等和数据库约束。

### 项目证据

- [缓存网关](../../../src/main/java/com/stock/system/stock/market/CachingLongbridgeMarketGateway.java) 与 [Redis 锁实现](../../../src/main/java/com/stock/system/stock/market/RedisMarketSharedCache.java)；原理和取舍见 [Redis 工程教学](../../engineering/redis.md#8-当前-redis-锁与-redisson-的关系)。
- [CODE-206E 验收](../../specs/002-stock-research/tasks.md#code-206e-最终验收证据2026-09-18)用两条独立 Lettuce 连接模拟竞争；它不等于多个真实 Longbridge sidecar 已获准并行部署。

### 可能追问

- Redisson 能替代哪些锁细节？哪些回源与降级决策仍要业务代码处理？
- 固定锁 TTL 到期后，旧请求为什么仍可能继续执行？

## PROJECT-06：请沿一次当天分时请求说明 Redis 缓存的命中与未命中

### 完整回答

> 工作台接口先校验用户对空间和股票的访问，再由分时 Provider 选择当天数据分支，调用缓存网关。网关按前缀、股票代码和市场日期生成 Key，先从 Redis 读 JSON：命中就解析出分时点列表返回；未命中则先合并本进程同 Key 请求，再用带 TTL 的 Redis 锁协调加载。取得锁后二次检查缓存，仍为空才调用 Longbridge 客户端（它也可能命中进程内短缓存），非空结果带 TTL 写回；未取得锁的请求等待别的实例写入，超时可受控回源。Redis 故障会被缓存层当作未命中并短暂冷却，不能把“缓存没取到”和“上游没数据”混为一谈。一次完整分时响应还可能读取交易日与前收盘价，不能声称只查一个 Key。

### 项目证据与复习

- [分时接口](../../../src/main/java/com/stock/system/stock/controller/WorkspaceStockController.java)、[缓存网关](../../../src/main/java/com/stock/system/stock/market/CachingLongbridgeMarketGateway.java)；逐层调用与命中／未命中细节见 [Redis 工程教学](../../engineering/redis.md#31-用当天分时串起一次真实请求)。

## PROJECT-07：每日目录同步失败，怎样避免破坏已有研究？

> 项目把外部证券目录作为需要验证的输入，按独立 run 采集，再核对来源时效、分页完整性和范围。通过后由 Java 单次入口事务 upsert，股票代码唯一约束与字段所有权保证 ID 不变，缺席股票保留，也不把已核验交易状态重置成 UNKNOWN。任务外层用文件锁避免同机重叠，数据库命名锁保护跨机导入。每轮留回执，只有提交且回执核对成功才更新最后成功指针；采集失败保留上一成功结果。数据库提交和磁盘指针不是同一个事务，提交后写指针失败仍可能发生，所以依靠幂等重试恢复，不能宣称分布式原子提交。股票身份保持，已有空间和研究周期的外键才不会断开。

代码与范围见 [目录同步设计](../../specs/002-stock-research/design.md#42-目录字段接入核对2026-09-08)，生产首次同步、隔离回滚和失败测试见 [CODE-206G／H](../../specs/002-stock-research/tasks.md#2026-10-07-v1-收尾目录部署与整体流程)。已验证首次成功和定时器安装，长期运行与主动告警仍需后续验证。

## PROJECT-08：为什么交易状态不能依赖价格或旧 K 线判断？

> 旧 K 线只能说明最后取得的成交数据日期，停牌和退市都可能没有新价格，所以系统直接查询长桥的 trade_status。即使没有有效价格，明确的停牌或退市仍独立保存。数据库分别记录最后确认和最后尝试，查询失败保留上次事实、页面显示待核实，不能把旧正常状态冒充本次确认。缓存保留原获取时间，条件更新拒绝旧响应覆盖新状态；开启新研究在股票行锁内重验。每日任务复用后端现有行情连接，每批最多 500 个代码，MySQL 命名锁避免同库后端重复跑，股票 ID 和研究历史保持。供应商不返回状态的证券仍是覆盖边界，不能根据目录缺席补猜退市。

代码路径、实际无报价退市样本和验证边界见 [BUG-010](../../engineering/bugs/BUG-010-trade-status-without-price.md)，运行与覆盖证据见 [CODE-206J](../../specs/002-stock-research/tasks.md#code-206j每日交易状态核实2026-10-08)。

复习时需能解释：为什么不能先清空 stock 再导入；为什么批处理、事务、幂等和互斥锁分别解决不同问题；为什么成功指针失败后允许重复提交。


## PROJECT-09：怎样把 AI 框架接入已有 Java 系统？

> 项目接入时先核对框架和现有后端的版本关系，用原后端测试建立基线，再在源码副本中适配 Boot、Mapper、JSON、Flyway 和测试替身。保持业务断言，副本回归通过后才把改动落到主工程；模型默认关闭，无密钥也能运行原业务，另验证实际打包 JAR 的 HTTP 认证边界。模型适配使用回环替身检查工具配对和输出转换，不把它称为真实模型质量验收。故障测试还发现配置 1 仍发两次请求，核对实际 RetryPolicy 后改为零重试，并用请求计数复测。框架接入后，权限工具、会话、报告检索和页面质量仍分别验收，不能由框架可用推断业务可用。

代码与实际运行见 [AG-CODE-002](../../specs/004-research-agent/tasks.md#9-ag-code-002正式后端框架接入2026-10-12)，失败与修复见 [BUG-011](../../engineering/bugs/BUG-011-spring-ai-retry-count.md)。复述时需解释：为什么不能只改 pom 就称兼容；怎样区分协议测试与真实模型评测；自动重试与正常工具循环各怎样限制；为什么不能用 AI 协作完成代替个人独立实现。

## PROJECT-10：研究助手的工具调用由谁执行，怎样限制？

> 用户在授权的股票周期里提问，Java 先绑定账号、空间和周期、准备有效历史及费用预留。模型只能提出观点、最新报价、短期日 K、受限财务或报告段落请求；Java 检查名字和严格参数，再调用对应 Service，把实际结果用相同 call ID 返回模型。模型根据结果写回答，Java 校验引用、当前权限与来源再保存。接财务后最多四次模型请求、三次工具尝试，错误也计次数，没有自动付费重试，费用预留与次数同步；用量跨请求累加，任何派发用量不明都不释放整轮预留。旧聊天价格不是当前价，行情依据保留真实时间与模拟标记；成员猜测不能当经营事实。财务先核实原报单位、利润及期间再由 BigDecimal 计算，模型不猜单位或自己算同比；恢复时还核对报告版本和金额，旧依据失效就隐藏整条回答。字段和引用合法仍不等于语义正确，因此程序边界用受控检查，模型理解再对照真实样本核对。

正文流式又多了一层边界：上游网络分块先组成完整结构，梳理按概览和完整数组、追问按段落校验，Java 核对引用、对应数字和当前来源后才临时展示，全回复通过后才入库。梳理预览允许后续成员暂缺，正式结果仍检查完整覆盖，不能因为早期概览通过就保存半份结果。Vue 将 draft 与 messages 分开，失败／停止撤回前者，刷新按原编号恢复任务而不再付费。取消后网络可能继续收尾取得末帧用量，因此“页面停止显示”“停止后续工具”和“供应商请求已结束”必须分清；两种生成共用原生流传输和收尾，但 WebClient 仍需要独立的完整请求大小、预算和派发守卫，同步 RestClient 的拦截器不会自动覆盖它。机制见 [设计 6.3](../../specs/004-research-agent/design.md#63-用户看到的状态)，细碎分块与慢消费暴露的顺序问题见 [BUG-020](../../engineering/bugs/BUG-020-native-stream-backpressure-order.md)，测试与真实样本见最新任务；不声称按字播放、任意问题可靠或本人已经掌握。

正式代码见 [ResearchQuestionService](../../../src/main/java/com/stock/system/agent/service/ResearchQuestionService.java)，完整链路复习见 [工具追问](../../engineering/agent-experiment.md#7-正式业务学习一次工具追问怎样完成)，早期真实四例及程序证据见 [AG-CODE-005](../../specs/004-research-agent/tasks.md#14-ag-code-005工具追问与真实样本核对2026-10-14)。财务仅官方年度报告限定覆盖，取数依据见 [第 17 节](../../specs/004-research-agent/tasks.md#17-官方原报限定覆盖与财务工具2026-10-14)，当前固定题集的真实语义核对见 [第 33 节](../../specs/004-research-agent/tasks.md#33-最终版本完整回归与原题集核对2026-10-21)，后续程序补修与实际版本沿最新 tasks。报告工具已接真实本地向量和有限章节原文，仍由 Java 绑定股票并在命中后校验权威版本；机制见 [报告接入](../../engineering/agent-experiment.md#12-报告检索如何进入正式助手)，不支持模型提交任意 URL。检索命中、结构校验、原文支持分别验收；008 的两份受审年报本机限定结果与仍待验范围见 [第 28 节](../../specs/004-research-agent/tasks.md#28-报告六题真实对照与财务正文防错2026-10-18)，不等于本人已能独立实现。可追问：提示词为什么不能代替 Java 授权？用量未知为什么保留预留？向量命中为什么不证明结论正确，旧报告被移除后应怎样处理旧回答？

HTTP 回包丢失时还要区分“客户端未收到”和“任务失败”：按原 requestId 找到本地运行，再恢复或轮询；不知道终态时不换新编号自动重试，否则无法利用幂等保护。观点撤回、失去权限或清空时，轮次和保存前的校验停止后续调用，费用与正文分别处理。代码与实际断线检查见 [006](../../specs/004-research-agent/tasks.md#15-ag-code-006记录变化与断线恢复2026-10-14)，复习见 [断线恢复](../../engineering/agent-experiment.md#8-正式业务学习断线后查原任务)。

报告更新与历史引用也要分开：当前查询用最新可用发布，旧回答仍核对当时的已发布版本；移除后业务状态同时阻止新检索和旧原文，不能因磁盘有旧向量就恢复。当前单机小语料用原子文件记录公开正文与状态，短锁外构建索引，再按代次／令牌核对发布，失败保留旧版；这不是 MySQL 后台任务队列。模型调用故障另存安全分类与运行编号，方便区分取数成功后的模型失败，未知 Token 仍保留费用预留。机制与本机边界只见 [设计 4.4](../../specs/004-research-agent/design.md#44-报告资料库与-rag-接入) 及 [排障说明](../../engineering/agent-experiment.md#模型失败如何排查)，不由本次实现推断腾讯真实故障已修复或本人已掌握。

检索取舍也应由问题集说明：关键词适合原词和产品名，向量补改写语义，两路先按同一股票／年度过滤、核对发布身份，再融合排名。项目已用冻结校准／留出题实际比较关键词、向量、混合及本地词法重排；重排出现首位倒退，所以默认关闭。复述时分清“找到了正确章节”“引用编号合法”“原文支持回答”三个层次，并说明小语料命中和单次耗时不能代表全市场质量或生产性能；参数、复现与坏例子见 [检索对照](../../engineering/agent-experiment.md#检索对照与报告回答评估) 和 [第 27 节](../../specs/004-research-agent/tasks.md#27-混合检索重排对照与报告评估入口2026-10-18)，不将这些工程证据冒充本人独立完成评测。

还要区分财务快照与展示文字：真实复测曾在合法引用下自行换算单位并写错金额，说明工具和结构检查都通过仍可能有事实错误。Java 在本轮实际取得并核实财务快照后检查新答案的数字与原单位，模型删除引用不能关闭校验；没有本轮财务取数但显式引用财务时仍检查。每段只按自身引用、缺口按最终答案的引用并集核对，查询过但未引用的资料不授权数字。错误结果不保存，已发生用量照常结算；它不保证科目与数字的语义对应，也不追溯改写历史回答。真实错误见 [BUG-012](../../engineering/bugs/BUG-012-financial-answer-unit-conversion.md)，缺口遗漏及引用触发旁路的离线复现、修复与范围见 [BUG-019](../../engineering/bugs/BUG-019-financial-gap-validation.md)，不能表述成“有引用就不会幻觉”。

报告事实的另一个真实坏例是把“其他原辅料”扩大成全部原料，强化 Prompt 后仍复现。当前选择把带报告引用的事实段落交付为完整受审原文摘录，保留模型的来源选择和其他材料解释；牺牲报告自由概括，换取原文限定直接保留。原文、混引拒绝与离线回放的边界见 [BUG-013](../../engineering/bugs/BUG-013-report-scope-generalization.md)，不能将程序纠正后的摘录算作模型原始概括全部正确。
