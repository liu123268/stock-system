# Redis 与缓存面试问答

这里保存 Redis 与缓存专题中高频、值得反复练习的基础题。项目已经使用的能力必须给出真实证据；项目未采用的方案只作为知识准备，不能包装成项目成果。项目实战中的 [自写锁取舍](01-project-engineering.md#project-05为什么行情缓存使用自写-redis-锁而没有接入-redisson) 和 [真实请求数据流](01-project-engineering.md#project-06请沿一次当天分时请求说明-redis-缓存的命中与未命中) 已有独立回答，这里不再复制；详细原理见 [Redis 工程教学](../../engineering/redis.md)。

## CACHE-01：为什么项目使用 Redis，而不是只使用 Java 进程内缓存？

### 完整回答

> Java 进程内缓存访问快、实现简单，但只属于当前 JVM，应用重启后消失，多个后端进程也不能直接共享。Redis 是独立服务，多个应用进程可以通过网络读取同一份缓存。本项目先保留 Longbridge 客户端的进程内短缓存，再在外层增加 Redis：同一进程的短时间重复请求可以直接复用，连接同一 Redis 的多个缓存客户端还能共享可重建行情。代价是增加一次网络访问和一个外部依赖，所以 Redis 故障时必须允许退回进程内缓存与受限回源，不能让缓存故障变成行情接口整体不可用。

### 与项目的关系和边界

- 项目只把报价、K 线、分时和交易日历等可重建结果放入 Redis；用户、空间、权限、研究周期和观点仍以 MySQL 为准。
- 当前真实证据证明两个独立 Lettuce 连接能够共享结果和协调加载，不证明多个真实 Longbridge sidecar 可以水平部署。
- Redis 解决的是跨进程复用，不代表所有数据都应该缓存；没有重复读取或性能证据的 MySQL 业务数据目前没有接入 Redis。

### 可能追问

- 本地缓存和 Redis 可以同时存在吗，读取顺序怎样设计？
- Redis 故障后为什么不能直接切换成 Mock 行情？

## CACHE-02：Redis 常见数据结构怎样选择？为什么本项目主要使用 String？

### 完整回答

> 数据结构要根据需要执行的操作选择。String 适合整体读写 JSON、计数和保存锁 owner；Hash 适合按 field 读写对象的一部分；List 适合从两端按顺序加入或弹出元素；Set 适合去重和成员判断；ZSet 在成员不重复的基础上增加 score 排序。本项目读取行情时需要按完整查询 Key 取得一整份结果，没有按字段局部更新的需求，所以把统一信封和行情值序列化成 JSON String。锁也只需要保存随机 owner，并用 TTL 和 Lua 完成获取、过期与安全释放，没有必要为了“用了更多数据结构”改成 Hash 或 List。

### 与项目的关系和边界

- JSON 数组保存在 String 中，Redis 仍把它视为一个整体；它不会自动获得 List 的逐项弹出语义。
- 项目没有使用 Redis Hash、List、Set 或 ZSet，也没有用 Redis 实现排行榜、消息队列或共享登录会话。
- 数据结构选择不能只看 Java 对象外形，还要看 Redis 端需要原子完成什么操作。

### 可能追问

- 保存对象时，String JSON 和 Hash 各有什么取舍？

## CACHE-03：缓存穿透、击穿和雪崩有什么区别？项目分别做到哪一步？

### 完整回答

> 缓存穿透是大量请求查询不存在的数据，缓存和下游都找不到，空结果又没有缓存，导致请求反复越过缓存；缓存击穿是一个真实热点 Key 恰好失效，大量相同请求同时回源；缓存雪崩是许多不同 Key 集中过期或 Redis 整体不可用，大面积请求一起压向下游。三者都表现为未命中后压力上升，但请求对象和形成原因不同，因此不能只用“加一个锁”统一回答。

### 与项目的关系和边界

- 穿透：行情入口先验证参数和本地可信股票目录，任意不存在的代码不会直接访问 Longbridge；但大量合法冷 Key 和真实股票持续返回空结果仍可能回源，项目没有使用布隆过滤器，也没有缓存空 List/Map。
- 击穿：同一 JVM 用 `CompletableFuture` 合并同 Key 请求，连接同一 Redis 的进程再用限时协调锁减少重复加载；等待超时允许回源，所以不是严格只调用一次。
- 雪崩：不同类型使用不同 TTL，写入时增加随机抖动；Redis 故障进入短暂冷却，所选 SDK／CLI 客户端继续保护并发和调用间隔，具体机制见 [ADR-002](../../architecture/decisions/ADR-002-longbridge-cli-sidecar.md)。项目尚未验证 Sentinel、Cluster、全局限流或完整熔断。

## CACHE-04：Cache Aside 怎样处理数据库与缓存一致性？本项目为什么没有“更新 MySQL 后删除 Redis”？

### 完整回答

> Cache Aside 由应用分别访问缓存和主数据源：读取先查缓存，未命中再读取主数据源并回填；写入通常先提交数据库，再删除缓存，让后续读取重新构建。它能减少双写缓存带来的乱序问题，但不能自动提供强一致性：数据库提交与 Redis 删除是两个系统的两次操作，删除可能失败，并发旧读也可能在删除后把旧值重新写回。短 TTL、重试、消息、订阅 Binlog 或版本号分别处理不同风险，不能不看业务就全部接入。

### 与项目的关系和边界

- 这是面试知识准备；当前项目没有把 MySQL 用户、空间或研究记录缓存到 Redis，因此没有对应的数据库写入后删缓存链路。
- 当前 Redis 的主数据源是 Longbridge。项目不能在供应商行情变化时执行删除，只能按数据变化速度设置 TTL，在有效期内接受短暂陈旧，到期后重新访问上游。
- 项目使用了“先读缓存、未命中加载、再回填”的旁路思想，但不能据此声称已经解决数据库与缓存双写一致性。

### 可能追问

## CACHE-05：热点 Key、大 Key、TTL 到期和内存淘汰有什么区别？

### 完整回答

> 热点 Key 描述同一个 Key 在单位时间内被频繁访问，关注的是访问次数；大 Key 描述一条 Key 对应的 Value 很大，关注的是单次传输、处理和内存占用。TTL 到期是应用为某条数据设定的有效期结束；内存淘汰则是 Redis 达到 `maxmemory` 后按照淘汰策略为新数据腾出空间，尚未到期的 Key 也可能被删。四者可以相互影响，但不是同一个问题：请求合并可以减少热点 Key 失效时的重复回源，却不会减少持续命中时的 Redis `GET`；设置 TTL 也不能证明单条 Value 不大或总内存一定足够。

### 与项目的关系和边界

- 当前分时 Key 可能因为被频繁查看成为热点；历史 K 线完整批次可能较大，但没有 `MEMORY USAGE` 等实测证据前不能直接称为大 Key。
- 项目用不同基础 TTL 和随机抖动降低集中到期风险；本机学习实例没有配置 Redis 数据集内存上限，这不代表生产环境不需要容量和淘汰策略。
- 当前同 Key 合并和加载锁主要处理失效瞬间的重复回源；命中率、Key 体积、`used_memory` 和 `evicted_keys` 仍需通过监控或测量判断，项目没有虚构性能结论。

## CACHE-06：RDB、AOF、主从复制、Sentinel 和 Cluster 分别解决什么问题？

### 完整回答

> RDB 和 AOF 主要解决重启后的数据恢复：RDB 保存阶段性快照，AOF 记录写命令并在重启时重放，恢复范围取决于具体策略。主从复制把主节点数据复制到副本，但只有复制并不等于故障后会自动选出新主节点。Sentinel 面向非分片部署，负责监控和自动故障转移；Cluster 还会把不同 Key 分片到多个节点，用于扩展容量与吞吐，并提供相应的节点故障处理。持久化、高可用和分片是三个不同问题，不能把“开了 AOF”说成服务不会中断，也不能把“有副本”说成已经完成自动切换。

### 与项目的关系和边界

- 这是知识准备；当前项目没有部署 Redis 主从、Sentinel 或 Cluster，也没有多节点故障切换证据。
- 本机学习实例关闭 RDB/AOF，因为其中只有可从 Longbridge 重建的行情缓存；这是开发环境选择，不能直接作为生产配置。
- 生产方案应根据可接受中断时间、回源能力、数据量、吞吐和运维能力决定，不为了简历机械加入集群。
