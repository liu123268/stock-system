# 需求与实施工作流

仅需求讨论、功能实施及技术选型时读取相应章节。教学沟通见 [项目入口](../../AGENTS.md)，带学方法见 [教学方法](teaching.md)。

## 需求与范围

- 先建立整个产品和当前模块的骨架，再为当前纵向闭环明确用户、场景、最少业务规则、权限、失败处理和验收标准；不要求在第一行代码前穷举整个阶段的全部字段和远期边界。
- 需求讨论负责决定“当前闭环做什么和为什么”，代码实施依据确认结果完成“怎么做”。两者可以在同一任务连续完成，不把短规格讨论机械拆成多轮对话。
- 需求存在多个合理方案时，分别用直白语言说明每个方案实际怎么运行，再明确比较核心区别、代价和适用场景，最后给出唯一推荐方案；用户回复“同意”默认确认推荐方案。
- 不用只有字母和术语的选项要求用户自行猜区别。用户尚无概念时，先讲清产品功能、学习内容、开发顺序、学习顺序、学习方式与掌握标准的总图，再按阶段进入原理和实现；不能展示地图后立刻转入接口、参数或源码细节。可逆的内部实现由 AI 给出并落实推荐做法，不以连续技术选择题代替讲解。只有用户要改变推荐结果，或涉及新的费用／授权、产品范围和不可逆操作时才补问；相互独立的问题可以合并，存在前后依赖时按依赖顺序处理。
- 当前纵向闭环只需满足最小开发准入：用户故事明确、权限和失败边界明确、涉及的核心数据关系可解释、接口与页面入口可落地、验收场景可执行。其余字段和远期能力在真正进入对应闭环时再确认。
- 开发顺序优先形成页面可见、用户可以亲手操作的纵向闭环，不能连续完成大量底层结构却长期没有可访问的真实页面；每个阶段应尽早把后端、前端和验证接成一个有成就感的小结果。
- Java 核心主线与阶段顺序见 [路线](roadmap.md)；空间访问边界可用后尽早进入股票与观点闭环，不等整个治理阶段验收，避免以基础设施收尾拖延可见结果。
- 规划以 30～45 分钟为默认时间盒。到达时间盒仍在扩展问题时，应缩小闭环、记录非阻塞待办并开始实现；只有会改变数据关系、权限、安全、外部成本或不可逆迁移的问题才能阻塞编码。
- 实施时不得顺手开始未确认的下一阶段。

选择下一项开发或学习任务时，按 [实习准备路线](roadmap.md#实习准备与阶段关系) 说明它补足的业务缺口或能力缺口；产品验收与个人能力分别判断，具体证据见 [教学方法](teaching.md#推进掌握与记录)。不能因为可继续增加页面或中间件，就自动把现有核心知识的应用核对排到项目全部完成之后。

## 技术选型

- 新技术必须同时说明：真实问题、候选方案、选择理由、引入成本、失败方式、测试方法和退出方案。
- 讨论技术路线、依赖、中间件、性能、简历深度时，必须对照 [技术学习参考](technology-reference.md) 的相关原始条目；评估整体学习路线或能力覆盖时再完整对照。
- 面向求职确定 Java 与 Agent 版本尺度或整体复核路线时，交叉查询头部与中型／中小、行业软件企业的近期岗位、求职者第一人称面经及项目作者复盘，并以官方资料核验技术事实；区分后端实习／应届、应用、平台、算法及资深社招，记录日期、必备／优先条件和来源边界。不能只按 JD 关键词判断项目难度，也不将匿名题单、培训宣传或个人感受当成统一招聘门槛。用具体产出、实际追问和验证证据建立标准，再讨论功能；当前依据见 [Java 与 Agent 求职能力对标](java-agent-market-benchmark.md)，目标或市场变化时重新核对。
- 为避免做到中途才发现关键条件不成立，接入前核对现有数据覆盖、授权／预算、版本兼容和模型能力；把未验证的关键依赖安排为最早的小实验，写明失败时的缩小范围或替代路径。代码审查、官方能力说明和真实运行证明分别记录，不能把“有实现路径”写成“已经保证效果”。
- 参考清单不是实施命令；实际采用状态只以 [实际技术栈](../architecture/technology-stack.md) 为准。
- 架构选择沿用 [ADR-001](../architecture/decisions/ADR-001-modular-monolith.md)，仅在其重新评估条件出现时重开选型。
- 引入效果使用可复现实验与真实代码证据评估。

## 完成闭环

需求、权限、校验、异常与事务一致性落实后，按 [测试规则](../engineering/testing.md) 选择足够的验证。任务完成证据写入当前 tasks，教学沉淀按 [文档维护](documentation.md) 处理。未通过验收的步骤不标完成；不越过失败进入依赖它的下一步。
