## 路线原则

## 实习准备与阶段关系

当前目标是 Java 后端实习。产品功能完成、代码验证通过和个人掌握程度分别判断；功能完成证据见 specs，学习目标对照 [技术参考](technology-reference.md)，不能用任务勾选推断用户已掌握。

2026-10-09 [岗位、面经与行业实践复核](java-agent-market-benchmark.md#5-2026-10-09-重新核查与计划对照) 后，主准备方向保持 Java 后端，包括 AI 业务团队；Agent 增量同时支持接受 Java 的应用工程岗位。明确要求熟练 Python／PyTorch、模型研究或高级平台内核的岗位须另查差距，不能宣称当前路线覆盖全部 Agent 职位。基础学习与 Agent 开发并行，不以把所有 V2 功能做完作为开始准备 Java 面试的条件。

开发主线先收口 [V1 Java 核心版](../product/requirements-v1.md)，再进入 [V2 第一阶段单 Agent](../product/requirements-v2.md)；求职准备从现有真实闭环开始，与开发并行，不等待下面所有阶段结束。V1 可独立作为简历与演示版本，尚未完成的功能如实注明；Agent 目标保留在 V2，其他产品增强仍按候选清单评估。

| 优先方向 | 从现有项目切入 | 可检查的准备结果 |
| --- | --- | --- |
| 核心业务与 Java 基础 | 登录鉴权、空间隔离、加入股票事务、研究周期；结合集合、异常、代理与 Spring 请求链路 | 能脱离现成答案讲清请求到数据库的过程，解释失败边界，并独立完成关键逻辑的小练习 |
| MySQL 与并发 | 邀请次数竞争、唯一约束、行锁、观点分页 | 能写核心 SQL、解释事务与锁；完成一次带数据规模、执行计划和前后对照的真实 SQL 优化实验，不编造提升比例 |
| Redis 与外部依赖 | 行情缓存、同 Key 回源合并、超时及故障降级 | 能说明 Key／TTL、数据库与行情来源的区别、锁的适用边界，并用已有测试解释失败场景 |
| 测试与交付 | JUnit／Mockito、真实 MySQL 集成测试、启动配置与部署 | 能独立设计正常和失败用例、判断测试证明了什么；完成可复现启动、环境配置与排错演示 |
| 基础与面试表达 | Java／JUC／JVM、网络、操作系统、数据结构算法和 Hot100；对应项目问答 | 按原技术目标持续练习；项目里没有的基础可做小实验，明确标为知识准备，不强塞业务实现；练习项目介绍、技术追问与现场编码 |

以上是准备方向和验收方式，不是已完成清单，也不另开一套与项目专题重复的课程。SQL 实验承接阶段 4，交付承接阶段 5，简历与复述承接阶段 7；具体证据仍放唯一工程／career 落点。

新增产品增强优先核对是否能补足上述能力缺口；现有场景足以练习时先吃透现有实现。MQ 仍保留“掌握一种、真实异步场景”的学习目标，主项目尚无合适场景时暂不接入；更复杂图表、额外市场、微服务、RAG／MCP 和多 Agent 不成为开始求职准备的前置条件。这里指可先用 V1 准备 Java 岗；完整 V2 的 RAG／MCP 仍须按 [第 6 阶段](#阶段-6java-agent-增量) 完成。

## 阶段 0：产品与工程基线

目标：开发前先统一名称、需求、角色、文档、规则和技术路线。

- 建立 `AGENTS.md` 项目规则入口与按场景读取机制；
- 整理交接、进度、规则、技术栈、Bug、面试和亮点文档；
- 收集并分析用户技术学习参考；
- 确定暂定名称并在正式发布前完成最终命名；
- 确认 V1 角色模型和功能边界；
- 评估 Spring Boot 维护版本；
- 确认单 Maven/Spring Boot 工程内按业务模块分包，并规定模块依赖与命名边界；
- 明确每阶段验收标准。

完成条件：新对话能够自动接手，文档无失效链接，技术参考与实际技术栈清楚分离，下一阶段需求可以直接实施。

## 阶段 1：研究空间最小闭环

目标：建立所有后续业务的数据隔离和权限基础。

- 查询当前用户加入的空间；
- 创建研究空间；
- 当前空间和空间切换；
- 生成、停用和使用邀请码；
- 成员列表和成员状态；
- 空间外个人资料入口、修改昵称和登录后修改密码；
- 根据有效成员关系和 `workspace.owner_user_id` 判断 OWNER/MEMBER，并落实每项操作规则；
- 最小超级管理员用户、空间状态和操作记录治理仍是 V1 必需范围，但调整到股票与多人观点核心闭环之后收尾，不在此阶段扩展额外后台能力；
- 非成员访问、跨空间越权、重复加入和事务回滚测试；
- 前端接入真实空间数据。

重点能力：关系建模、RBAC、事务、唯一约束、幂等、越权防护和集成测试。

当前详细范围、设计和实施顺序见 [SPEC-001 研究空间规格](../specs/001-workspace/requirements.md)。

阶段衔接：空间访问和归档边界可用后，进入 [SPEC-002](../specs/002-stock-research/requirements.md) 的股票与初始观点闭环；真实 pull 行情正确性闭环之后，验收 Redis 共享缓存及故障降级，再进入研究生命周期与多人观点时间线，随后返回个人资料、空间改名和超级管理员最小治理。当前具体任务与阻塞只见 [status](status.md)，不在路线保存另一份下一步。Redis 不与 WebSocket/SSE 捆绑实施；目录完整性、每日同步与部署可靠性按 SPEC-002 任务分别验收，不把它们隐含为行情页面完成的结果。

## 阶段 2：股票与行情闭环

目标：让成员通过标准股票数据建立共享自选股，并在首次添加时同时发表初始观点，形成用户可见的第二段核心闭环。

- 验证合法、稳定的 A 股与港股数据提供者；
- 定义 `MarketDataProvider` 适配接口；
- 股票基础信息同步和搜索；
- 最新可用价格与行情时间；
- 基础报价先完成批量、限流和进程内短缓存，再接 Redis 共享层；完成度只见阶段 tasks，不在路线保存另一份验收状态；
- 缓存 Key、TTL、数据库一致性、穿透/击穿/雪崩防护和 Redis 不可用时的降级边界，以 [SPEC-002 设计](../specs/002-stock-research/design.md#46-redis-共享行情缓存与访问保护) 为唯一正文；
- 添加共享自选股和初始观点的事务；
- 同一空间同一股票防重复；
- 行情失败和模拟数据标识；
- 自选股列表和状态筛选。

重点能力：第三方 API/sidecar 适配、Redis 共享缓存、限流与故障降级、数据来源可信性、事务和组合唯一约束；动态推送仍在有真实需要时再验证 WebSocket/SSE。

## 阶段 3：多人观点与复盘

目标：形成项目区别于普通股票 CRUD 的核心功能。

- 初始观点和后续观点更新；
- 作者与时间由后端产生；
- 多成员观点时间线；
- 股票详情、最新行情和关注以来表现；
- 简单历史走势；
- 观点撤销或状态变化，不物理覆盖历史；
- 近期观点动态和空间概览。

重点能力：时间线建模、审计性数据、分页查询、前端状态管理和可视化。

任务承接：研究生命周期由 SPEC-002 PLAN-207 跟踪；时间线规模、近期动态与详情行情／价格变化分别由 CODE-209～211 承接。它们与返回 SPEC-001 的账号／治理收尾共同构成 Java 核心 V1，不能因时间线页面可用就宣称阶段 3 或 V1 已全部完成。

## 阶段 4：性能、并发和可靠性

候选内容：

- 在阶段 2 已接入的 Redis 行情缓存上补充容量、淘汰、热点 Key 和更大规模故障演练；
- 登录失败限制或接口限流；
- MySQL 组合索引、覆盖索引、`EXPLAIN` 和慢 SQL；
- 定时行情同步和重复执行防护；
- 在业务阶段已有正确性保护上补更大并发的性能实验；重复添加、邀请码次数和旧页面误操作等正确性问题不得推迟到本阶段；
- 可复现的性能测试和基线数据。

引入条件：核心业务链路先正确运行，并且每项优化有可测量的目标和前后证据。

## 阶段 5：异步、可观测性和交付

Java 核心交付与后续增强分开安排：可复现启动、部署配置、日志排错、备份恢复说明及 CODE-206H 环境验收先服务于核心版演示；MQ 与更完整监控按真实问题逐项推进，不把全部候选中间件列为核心版交付前置。具体技术状态见实际技术栈。

交付与增强内容：

- 在 RocketMQ 与 Kafka 中评估并只选择一种 MQ，处理非核心动态、通知或数据同步；后续 RAG 的耗时资料导入／索引重建也可作为真实异步场景候选，先与受控线程池／任务表比较，不自动增加 MQ 依赖；
- 消息幂等、重试、死信和失败补偿；
- Actuator 健康检查；
- 结构化日志、请求追踪 ID 和关键指标；
- Docker Compose 统一必要服务；
- Nginx 托管前端和反向代理；
- 配置环境变量化；
- 部署、备份与恢复说明。

不为了展示消息队列而把强一致核心事务错误地异步化。

## 阶段 6：Java Agent 增量

版本归属：V2。V1 独立验收之后实施；能力层次和产品边界见 [V2 规划基线](../product/requirements-v2.md#3-正式讨论采用的规划基线)，计划技术与兼容性见 [技术规划](../architecture/technology-stack.md#32-v2-agent-技术规划基线)。本节维护功能与学习顺序的地图，不替代详细用户故事、设计和验收任务；实际进度只见 [项目状态](status.md#当前阶段与下一步)。

目标：在完整 Java 业务系统之上增加可控、可追踪、可测试的 Agent 能力，使其成为“Java 后端 + AI Agent 应用工程”项目，而不是独立聊天 Demo。

### V2 功能与学习地图

2026-10-09 用户要求先形成全貌，不立即进入调用、参数或代码细节。地图分别说明产品功能、学习范围与深度、开发／学习顺序和学习方式；后面的详细规格在对应阶段使用，不要求先理解所有技术名词。

#### 产品做出的功能

既有 Java 系统继续负责用户、空间、股票、观点、数据与权限；新增研究助手负责围绕这些资料进行整理、问答和追问。用户在现有单股研究页使用同一个助手，产品方向与访问边界只见 [V2 需求](../product/requirements-v2.md)。

| 功能 | 用户能做什么 |
| --- | --- |
| 研究梳理 | 点击按钮，看到最新可用报价、成员看法、判断变化和待核对事项 |
| 行情与财务问答 | 询问报价、有限期间的价格变化、已覆盖财务指标和可比变化，得到来源、时间及口径 |
| 公司报告问答 | 询问已入库报告中的业务说明、管理层解释和风险，得到相关段落依据；这是必做 RAG 功能 |
| 连续追问与个人对话 | 围绕当前研究继续问，离开后能恢复自己的聊天，主动清空，切换对象不串资料 |
| 查看依据与缺口 | 打开观点、数据快照或报告段落；无资料、无权限或不能支持结论时有明确反馈 |

报告库由系统维护、脚本导入，普通用户不用上传或建库。能回答的范围由实际数据覆盖和当前权限决定。另完成至少一个 MCP Server 的学习实践，让标准客户端实际发现并调用受控工具；通达信／Wind 接入、观察条件核对和空间变化简报继续保留在后续方向。

#### 学什么、学多少与学到什么程度

核心学习量按八组主题组织：做一个 Java 业务 Agent 闭环，实际掌握一种 Java AI 框架、一种向量库，并实现或接入至少一个 MCP Server。八组主题按功能相互配合，框架随模型、工具、会话与检索的实现学习，不另开一门要先学完全部组件的课程。技术名称、组件和完整原始目标的对应只见 [能力覆盖表](../architecture/technology-stack.md#原始-agent-目标覆盖与验收)，以下是初学者的理解与练习地图。

| 学习主题 | 这组知识解决什么 | 本项目的掌握标准 |
| --- | --- | --- |
| 模型基础与资料组织 | 知道模型怎样生成回答、能力局限，以及回答时需要哪些资料 | 能解释为何会编造、为什么需要外部资料，区分资料检索与训练模型；知道 Token／上下文、Embedding 和 Attention 的作用；能修改模型输入检查效果。原理达到解释层，不要求训练或数学推导 |
| 工具与任务流程 | 让助手根据问题查询允许访问的数据，知道何时继续、停止或报告失败 | 能独立写一个受限只读查询的关键逻辑，解释它怎样被使用，并处理越界或查询失败 |
| RAG 报告检索 | 从系统报告库找到相关内容，支持有依据的回答 | 能独立搭建一条小型报告检索问答链路，解释为何检索失败或引用不支持结论，并比较一种改进的效果 |
| 会话与记忆 | 让追问保留必要上下文，正确保存、恢复、清空与隔离 | 能实现或修改关键会话逻辑，说明保存的聊天与本轮提供给模型的资料有什么关系 |
| MCP | 让工具按统一规则供客户端发现和调用 | 至少完成一个 Server 的实际接入或实现，客户端真正用到工具；能解释它与普通接口、模型选工具的关系 |
| 一种 Java AI 框架 | 用一套 Java 组件组织模型、工具、会话、报告检索和流式回答 | 主选 Spring AI，经兼容验证后实际使用；能修改配置或关键调用、定位问题，并说明框架替我们做了什么 |
| 可靠性与安全 | 处理无权限、超时、重复请求、并发、费用和资料中的诱导文字 | 能给关键请求设置边界，设计正常与失败检查，并解释为什么交给 Java 控制 |
| 评测与排错 | 判断回答是否有依据，比较修改前后效果并找出故障阶段 | 能维护带依据与评分规则的固定问题集，核对查询、检索与回答，记录耗时和费用；完成真实失败的定位、修改与复测，保留前后比较 |

重点深度是核心逻辑能够独立解释、修改、编写与验证，尤其是工具、RAG、会话和质量判断。框架、向量库与 MCP 要实际使用并能排错；只读过概念或安装依赖不满足这一层目标。完整框架源码、复杂平台和算法研究不作为本版完成条件。长期记忆、模型路由等扩展先理解作用；高级规划、Multi-Agent、Graph RAG 按原目标后学。基础 Python 随脚本／必要适配练习，Java 保持主语言；脚本基础不等于满足 Python 主语言应用岗，若后来明确投这类岗位，再补独立 Python Web／API 实现能力。Skills／Harness 先对应任务组织、运行控制与评测理解，不为名字另建平台。

#### 做的顺序与学的顺序

开发顺序以能逐步使用的产品结果为单位；学习顺序以理解依赖为单位。先把全貌讲清，再学习模型与资料的基础，然后在做页面和工具时掌握一套框架，继续学会话、RAG、MCP，最后综合回顾和排错。无需先上完八组理论再开始动手；安全、费用、测试和评测穿插每段。

| 开发段 | 要交付的结果 | 详细任务对应 |
| --- | --- | --- |
| 1. 提前验证关键条件 | 分别确认模型、财务资料、报告检索和框架有可检查的实现路径 | AG-CODE-001／001F／001R／002 的提前验证 |
| 2. 第一张真实页面 | 当前研究周期可梳理真实观点，带报价与依据；有最小个人会话保存和失败反馈 | AG-CODE-002／003／004 |
| 3. 数据查询与追问 | 实际完成观点、报价、有界日 K 和核心财务问答，来源及数字可核对 | AG-CODE-005／005F；工具边界沿 003 |
| 4. 完整会话与交互 | 返回可续聊，清空与权限变化有效，流式显示有结束／失败状态，迟到结果不串对象 | AG-CODE-006／007；会话基础沿 004 |
| 5. 报告 RAG 接入 | 同一助手能检索报告、回答并查看段落，资料导入、更新和移除可核对 | 提前 AG-CODE-001R，正式 AG-CODE-008 |
| 6. MCP 实践 | 一个客户端真实发现并调用受控工具，授权失败和故障可处理 | AG-CODE-009 |
| 7. 整体收口 | 固定问题集、浏览器回归、费用与故障核对、演示及项目表达 | AG-CODE-007／008／009 的整体核对，交付沿阶段 7 |

以上分组不代表七次对话或固定工期，整体难度仍为中等偏高，主要在资料、权限、上下文与回答质量。前置验证和学习理解各自记录，不能因 AI 已跑通程序就判断学生已经掌握。

#### 怎样学与完成标准

每一段采用同一节奏：先看这个功能供用户做什么，再解释它解决的问题和必要原理；随后一起完成一小块，让学生独立编写或修改关键部分；再验证正常与失败情况，最后用自己的话讲述设计。每段保留可回看的复习提纲和不懂的点，不要求每小节答题，也不将复制完整代码作为练习完成证据。

Java 尚未学完时可以从 Agent 概念、角色与资料流开始，也可在讲解下阅读短小的自造样本实验；不以学完 JUC／JVM、独立写完整接口或完成所有 Java 专题作为入门条件。进入动手时，逐步补方法、参数与返回值、对象、集合和异常，再结合实际工具补 HTTP／JSON、Service 与 SQL、权限检查。哪个功能暴露基础缺口，就先做对应的小练习，再回到该功能；不直接跳到大段框架源码或多个服务集成。

Agent 教学与既有 Java 动手、MyBatis 等专题并行；按当前独立表现从骨架方法到关键业务逻辑逐步提高要求，不能从“Java 学到一半”推断已经能独立开发。并发、事务、缓存与 JVM 继续沿原路线学习，在对应功能中加深，不因 Agent 入门而关闭原学习交接。教学起点沿 [模型、Java 与工具的数据流](../engineering/agent-experiment.md#11-先分清模型java-和工具)，实验操作及源码在理解角色后再进入。

本版个人能力目标：能说明 Java 模块和 Agent 模块各自职责；能面对一个新问题设计需要哪些有权资料、完成关键查询与回答逻辑；能独立跑通小型报告检索问答并核对依据；能排查一次错误并用简短项目介绍讲清选择理由、数据路径、失败处理和验证结果。功能完成证据与这些个人掌握证据分别记录。当前先建立总图，接口请求、参数、表结构和实验源码在对应阶段再讲。

个人学习进展用三类实际结果检查，随阶段完成，不另开一套课程：

- Java：从骨架逐步到独立完成一个受权限约束的接口或业务修改，写必要 SQL／测试并定位故障；数据库实验与基础面试准备沿本文件前述路线，不因 Agent 页面可用而关闭。
- Agent：独立新增或修改一个受限工具，再在报告功能中独立修改一种检索策略；能解释数据怎样进入模型、依据怎样检查，以及一次失败发生在哪一步。
- 项目表达：复现一轮修改前后评测和一个真实坏例子的修复，完成可复现启动与短演示；简历使用实际覆盖、次数和测量结果。真实使用反馈有则记录，没有流量时注明小范围验证，不编造用户量、QPS 或准确率。

上述是学习检查方式，不是企业统一录用线，也不保证固定工期。项目实现与 AI 实验可由协作先验证，个人独立能力仍需通过这些练习确认。

第 1 段的模型、财务、RAG 和框架验证需要各自取得独立证据，不能相互替代。财务源 AG-CODE-001F、报告解析与中文检索 AG-CODE-001R 要在主业务大量投入前提前验证；主框架兼容在隔离环境验证后再改主项目。兼容未通过时用现有直接 Java HTTP 路径保留实验和阶段成果，框架实践仍需另验。正式 RAG 页面在第 5 段接入，不表示到那时才第一次检查报告能否读取。验证方法和失败替代只见 [技术规划](../architecture/technology-stack.md#34-可行性验证与知识安排)。

技术主线沿用 Java、Spring Boot、现有数据库与 Vue，模型使用用户选定的官方 DeepSeek；Java AI 框架主选 Spring AI，必须实际使用并验证兼容。RAG 另需文本向量模型和一个向量库，Qdrant 是待验证候选；会聊天的模型调用成功不证明这些已具备。具体版本和采用状态只维护在技术栈，不要求用户预先选择内部参数。基础 Python 随评测／适配练习；原 Java 基础、SQL、Redis、真实异步 MQ 等路线继续保留，不强行成为第一个助手页面的依赖。

从最早调用起落实权限、参数和引用校验、输入范围、超时、有限调用、基础用量与失败样例，再逐段加深；第 7 段负责整体收口，不能将这些保护推迟到最后。初次梳理是 Java 先读取所需资料的固定流程，追问才验证模型按需选工具；前者成功不能代替后者。网页主链路关闭 Agent 后仍要保留 V1 的正常业务。

### 后续需求在地图中的位置

观察条件核对、空间变化简报与通达信／Wind 接入期望继续保留，范围与先后沿 [产品后续方向](../product/requirements-v2.md#32-后续需求方向与外部数据期望)。建议先做已有数据能核对的明确条件、用户主动生成的有限空间简报；外部数据先验证一个有授权的只读查询。它们不挤入首次页面，也不因在地图中出现而标为已接入或已确认全部细节。

自动荐股和自动交易不进入本版。总图之后按上述学习顺序从基础概念推进，具体技术问题随对应实验落实；涉及新账号、预算或生产开放的决定在启用前说明具体方案，不让它们阻塞概念教学。

验收时须证明工具调用和最终回答可以追踪，关键问题有稳定测试集，失败时不会写入错误业务数据；权限与工具范围以 [V2 需求](../product/requirements-v2.md#2-已确认范围与边界) 为准，学习覆盖逐项沿 [原始 Agent 目标对照](../architecture/technology-stack.md#原始-agent-目标覆盖与验收) 核对，阶段成果不代替未完成的 RAG／MCP／框架实践。
