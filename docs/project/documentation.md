# 文档职责与教学材料维护

场景读取和新规则处理见 [规则入口](project-rules.md)。本文件只规定文档内容边界和材料准入。

## 唯一正文与派生视图

| 内容 | 正文位置 | 其他位置的边界 |
| --- | --- | --- |
| 当前状态 | `status.md` | tasks 保留逐项证据；README 只放一句进度并链接 |
| 当前阶段需求／技术方案／实施证据 | 对应 specs 的 requirements／design／tasks | 分别回答做什么／怎样做／做到哪里；用规则编号关联，不复制整段 |
| 已实施数据模型 | Flyway 可执行结构、`architecture/data-model.md` 建模理由 | 阶段 design 只说明该流程怎样用表，不复制字段表 |
| 技术 | `architecture/technology-stack.md` 实际采用；`technology-reference.md` 原始学习输入 | 输入不是实施命令；原始文字不得改写或删减，应用分析只链接实际状态 |
| 工程教学 | 对应 engineering 文件；认证教学在 `architecture/authentication.md` | 按主题保存核心原理、项目代码路径和易错边界的复习提纲；不另建重复 learning 目录 |
| 产品目的、视觉、面试 | product-principles／ui-design-system／career | PRODUCT 是工具摘要，README 是公开摘要，HTML 地图是展示快照；均不新增独占规则 |

README、PRODUCT、功能地图和亮点材料只在面向读者的信息或里程碑变化时更新；面试问答可随专题学习补充。允许最少背景便于独立阅读，完整过程和数值证据使用链接；它们不成为开发前必读项。

## 日常维护

- 文档维护的基本要求是“不冗余、不缺漏、不多不少”：保留完成该文档职责所需的内容，不重复维护同一事实或规则，不增加未经确认的要求，也不遗漏已确认的要求、产品决定、教学、重要 Bug 和面试材料。这是每次整理都要执行的底线，不是只在全面审计时执行，也不以字数或文件数衡量。
- 整理前确认受影响内容的唯一正文和独有信息；整理后对照用户要求、当前实现与验证证据，核对遗漏、重复、冲突、状态和引用。需求尚未实现时保留目标并记录差距，历史证据注明日期和适用阶段；合并或迁移后仍能找到原有重要内容。检查范围按 [场景路由](project-rules.md) 选择，不因此要求每次重读全部文档。
- 确认需求就写 requirements，确认方案就写 design，验证完成就写 tasks；不要等下一次对话或用户提醒。
- 教学对话可以详细解释、反复推演和使用比喻；工程文档是供遗忘后快速找回概念、推理主线与代码位置的复习提纲，不复现整堂课。按主题合并细碎知识点，保留核心原理与必要因果、项目数据流或代码入口、易混点和适用边界；有助于回忆的短例子可以留，但不逐项存放长篇比喻、临时例子或问答过程，也不设机械字数上限。
- 教学中的初版解释、比喻和临时学习安排先留在对话：核对事实与项目适用范围，解决已暴露的理解问题，再把稳定的要点写进原主题；不因刚讲到一个知识点就立刻增加文档。每完成一个主题（包括没有代码改动的教学）检查是否缺复习必需的结论；已覆盖则不改，基础知识和本专题应懂但项目未采用的技术也不能仅因“不新”而漏记，后者标为知识准备。用户明确表示没听懂或指出讲法有问题时，不能把该讲法当作已定稿；也不把确认每条笔记的负担交给用户。
- 若已写材料后来被证伪、被否定、超出允许范围或不利于理解，主动核对受影响处，直接修正、合并或删除原文并修复引用；不在旧说法后追加一段相反解释，也不留下互相冲突的面试答案。未验证推测不能写成项目事实；历史方案注明已替代，最新代码教学与历史复盘分清。
- 专题材料难以浏览时，先合并重复内容并改善主题导航；仍过长则按可独立复习的知识块拆分并修正链接，不为每个术语单开文件，也不靠删除必要知识硬控体积。开发任务仍按场景只读相关材料。
- 每完成一个已验证的纵向闭环、重要技术接入或里程碑，AI 不等待用户提醒，主动检查工程教学、重要 Bug 复盘、项目亮点和分领域面试问答是否需要同步；已覆盖的知识用链接衔接，不机械追加重复内容。
- 不创建空标题文档、无意义的跳转文件或重复目录；删除文件先迁移独有信息并修正全部引用。导航只在结构变化时更新。
- 普通文档修改检查受影响文件及引用；结构大改可用 [文档检查脚本](../../scripts/check-docs.py) 检查本地链接并统计默认读取体积。统计不作为删减重要内容的硬门槛，脚本也不能证明自然语言没有语义冲突，仍需审阅相关规则。
- 开发库版本、当前进度、最新验证集中在 status，且标明验证日期。目录与模型只描述稳定结构，不各自保存一份环境状态。

## 交接内容与交接要求

`status.md` 承担当前交接：做到哪里、阻塞与未完成事项、最近验证、下一步及相关任务链接；稳定环境链接 development，详细证据链接 tasks，不复制全部历史。

用户对交接的写法、保留内容或更新方式提出长期要求时，在本节修改对应要求；本次进度写入 status。更新进度不能覆盖长期要求，也不能只在聊天或某次交接快照里记录要求。接手时通过项目入口和场景路由找到它们，不要求用户重述。

## 重要 Bug 准入

根因不直观且有教学价值，涉及框架、权限、事务、并发、缓存或部署，可能复发，对多个模块或用户数据有影响，或能形成有价值的面试追问时，才建立 `engineering/bugs/BUG-三位编号-简短英文主题.md`。

内容包括现象、影响范围、排查、根因、修复、验证、预防和面试转化。预防要求若已在测试或开发规则中生效，引用对应章节，不复制另一套执行规则。普通小错误不单独建复盘；若其中有值得复习的通用原因或排查方法，补进对应工程教学主题，不让学习收获只留在聊天里。

## 面试与亮点

- 工程教学保存能找回理解的必要解释；career 只把本专题高频、值得练习的问题合并成简洁可复述的回答，不为每个零碎概念各写一题，项目证据和较长原理用链接承接。亮点只写已实现、已验证的能力，不把学习中的知识当作项目成果。
- 面试问答既可来自真实项目经验（已验证的技术取舍、数据流、失败边界或重要 Bug），也可来自本专题必懂而项目尚未采用的基础或替代技术；后者明确标注“知识准备／项目未采用”，解释原理和不采用的原因，不伪造实现证据。它不是进度文档，不逐项罗列待办；当前进度只见 `status.md` 和对应 tasks。
- 为解释取舍确需交代早期状态时，明确写成“历史背景”，随后说明代码怎样演进以及证据在哪里，不能把会过期的阶段状态写成答案结论。尚未实现的候选架构不得提前包装成面试亮点。
- 不建只负责跳转的面试索引；按技术领域拆完整问答，文件名为“序号 + 领域”，问题使用稳定领域编号，如 SEC-01、DB-01。
- 项目经验题写明场景、完整回答、代码或测试证据、可能追问和当前边界；纯知识题写明概念、例子、与项目的关系及未采用边界，不硬凑项目证据。已有详解使用链接，不再复制排查全过程。
- 文件过长按知识边界拆，不建无意义的 part-2、part-3。候选技术、历史包体积或未复现性能不能冒充当前成果。
